# API Development

## 目的と適用範囲

新規API開発を、確定した仕様と各ディレクトリの規約に従って完了させる。詳細設計が未完成でも、大まかな処理フローと仕様の根拠が提示されていれば詳細化から開始する。既存成果物がある工程は現状との一致を確認し、不足分を作成・更新する。

このスキル自体の編集依頼ではAPI開発を実行しない。ユーザーが工程を限定した場合はその範囲を守り、このスキルを追加工程の実行許可と解釈しない。

本文中のパスはリポジトリルート基準、相対リンクはこのファイル基準とする。

## 作業範囲と判断の原則

- ユーザーの明示指示、適用される `AGENTS.md`、対象層のコーディング規約に従う。規約の優先順位はリポジトリ側の定義に従い、このスキルで上書きしない。
- 業務仕様・公開契約を推測で確定しない。既存コードは実装の参考とし、仕様との不一致を既存動作に合わせて黙って解消しない。
- 命名・配置・責務分離など、確定仕様を変えず規約へ適合できる事項は自律的に設計・実装修正する。応答、入力条件、所有権、状態遷移、保存内容、副作用が変わるか判断できなければ中断する。
- 対象APIに必要なファイルだけを変更する。無関係なエラー修正、共通基盤の刷新、ライブラリ追加、規約の緩和を行わない。
- migrationが必要なら規約に従い作成するが、この開発手順から実行しない。`sync`、DB作成、既存データの一括削除でテスト環境を自動補正しない。

## 1. 着手前の確認

1. `git status` でブランチと未コミット変更を確認し、ルート `AGENTS.md` のブランチ・既存変更保護の手順に従う。
2. 対象API、機能領域、処理名、仕様の根拠、対象外を整理する。ユーザー指定資料を全文読み、関連する基本設計・詳細設計・現行コードを照合する。資料の場所が不明ならリポジトリ内を検索する。
3. 変更予定の文書・コード・テストに適用される上位と対象ディレクトリの `AGENTS.md`、`docs/codingRule/backend/` の対象層の規約を読む。
4. 対象のroute登録、middleware、validator、controller、usecase、service、型、Model・associate、migration、既存テスト・fixtureを確認する。実ディレクトリ名は現行の `controllers`・`usecases`・`services` 等に合わせる。
5. 関連Todoがあれば [Todo運用](../../../docs/todo/AGENTS.md) に従って全文と完了履歴を確認し、旧提案と確定済みの仕様を区別する。
6. HTTPメソッド・URL、入力・出力、認証・認可、状態条件、DB操作、エラー、副作用について未確定事項を洗い出す。実装や期待結果を決める情報が不足していれば、詳細設計を確定する前に中断する。

開始時に対象APIと予定する成果物・検証範囲を短くユーザーへ伝える。既に許可された作業について、工程ごとの承認待ちは設けない。

## 2. 詳細設計の作成・更新

成果物：`docs/design/backend/detail/<機能領域>/<処理名>.md`

- [詳細設計の共通ルール](../../../docs/design/backend/detail/AGENTS.md) に従い、大まかな仕様を実装・テスト可能な粒度へ詳細化する。既存設計があれば更新し、重複作成しない。
- API契約、各層のファイル・関数・型、処理順、所有権・状態条件、DBの取得・保存対応、transaction・排他・再送、副作用、エラー、テスト観点を対象機能に応じて明記する。
- 仕様の根拠、現行実装、提案、未決定事項を区別する。DB反映済みか不明なら明記し、Modelやmigrationの存在だけで反映済みとしない。
- 規約違反は確定仕様を維持できるものだけ修正する。仕様変更が必要、または維持できるか曖昧なら中断する。

次へ進む条件：設計と規約が整合し、実装・テストの期待結果に影響する未決定事項が解消していること。

## 3. 本番コードの実装

成果物：`server/src/` 配下の対象APIに必要なコード。DB変更が必要なら関連Modelと新規migration。

- 詳細設計に従って各層を実装し、Routerの登録・接続まで確認する。
- 設計の記載漏れが見つかっても、確定仕様と規約から一意に補える内容は設計へ反映して続行する。新しい業務判断が必要なら中断する。
- 対象APIに起因する型・import・接続の不整合は修正する。対象外の問題は勝手に直さず、進行を妨げる場合はTodoへ記録して中断する。

次へ進む条件：設計した経路が実装され、設計とコードの差異が説明・解消されていること。

## 4. テスト設計書の作成・更新

成果物：`server/test/docs/architecture/<機能領域>/<処理名>.md`

- [テスト設計の共通ルール](../../../server/test/docs/architecture/AGENTS.md) に従い、詳細設計と本番コードを照合してケースを設計する。期待値は確定仕様を根拠とし、実装の現状だけに合わせない。
- ケースID、検証レベル、前提・入力・手順・期待結果、モック境界、fixture、配置、実行コマンド、完了条件を対応付ける。
- 正常・異常・境界・条件分岐・状態遷移に加え、所有者偽装、途中失敗、後続未実行、非対象データ不変、再送・競合を対象の責務に応じて検討する。該当しない観点は理由を示す。
- 単体、HTTP接続、実DBの保証を分ける。未実装・未実行の範囲、軽微な未確定事項も記載する。期待結果や実行可否に影響する未確定事項があれば中断する。

次へ進む条件：必要な検証観点がケースへ対応し、期待結果と実行前提が確定していること。

## 5. テストコード・fixtureの実装

[テスト配置規則](../../../server/test/AGENTS.md) と各層の `AGENTS.md` に従う。

| 成果物         | 配置先                                                |
| -------------- | ----------------------------------------------------- |
| 単体テスト     | 対象本番コードに最も近い `server/src/**/test/`        |
| 結合テスト     | `server/test/integration/<役割>/<機能領域>/<処理名>/` |
| fixture・setup | `server/test/fixtures/<機能領域>/<処理名>/`           |

- 結合テストの役割は配置規則と検証対象に合わせる。実DBを使うテストは [database規則](../../../server/test/integration/database/AGENTS.md)、usecase・HTTP接続等は [usecases規則](../../../server/test/integration/usecases/AGENTS.md) を読む。
- [fixture規則](../../../server/test/fixtures/AGENTS.md) に従う。既存の準備処理を再利用する場合はimport時のモック・hook・DB接続・cleanupまで確認する。
- 設計ケースとテストの対応を追跡できるようにする。対象の実処理をモックして同じ処理の保証とせず、通過させるためにassertionを弱めたり本番コードへテスト専用分岐を追加したりしない。

次へ進む条件：設計した必要ケースが実装され、DB接続・外部通信の有無と実行前提を確認できていること。

## 6. 実行・レポート・修正

成果物：`server/test/docs/report/<機能領域>/<処理名>.md`

1. 対象ファイル・ディレクトリを明示して、設計した単体・結合テストを実行する。`server/` でのコマンド例は `npm run test:run -- <対象パス>`。実際の対象パスに置き換え、無指定で全テストを起動しない。
2. 実DBテストは、接続前の `.env.test` 由来の設定検査、接続後の実DB名 `test_db` の確認、必要なスキーマ検査を全接続で行ってから書き込む。ガード不成立やスキーマ不足は自動補正せず中断する。自作ID限定のcleanup・全処理回収・接続終了まで確認する。
3. `server/` で次を実行する。通常lint対象外の変更TSは対象規約に従って追加検査する。

    ```bash
    npm run lint
    npm run typecheck
    ./node_modules/.bin/tsc --noEmit -p test/tsconfig.json
    ```

4. [レポートの共通ルール](../../../server/test/docs/report/AGENTS.md) に従い、実行日・ディレクトリ・コマンド、実出力に基づく結果、設計ケースとの対応、保証範囲、失敗・skip・未実行・未実装を記録する。初回・修正案・修正後の結果は同じレポートへまとめ、最新要約と履歴を区別する。
5. 失敗、ロジックの誤り、必要ケースの未実行があれば原因を切り分け、修正ID・元ケース・対象ファイル・原因・修正方針・期待結果・未達事項を記載する。
6. 確定仕様に沿う対象範囲内の実装・テスト・fixtureの誤りは修正し、設計書も整合させて対象テストと影響する回帰を再実行する。コードを再変更したら該当する静的検査も再実行する。
7. 完了条件を満たすまで原因に対応した修正・再検証を続ける。同じ失敗に新しい根拠や修正方針がなくなった場合は、同じ実行を繰り返さず中断する。仕様変更や対象外修正が必要になった場合も中断する。

接続・実行権限の不足は仕様不備と区別し、実行環境の承認手順に従う。権限の許可を別DBの使用やDB変更の許可と解釈しない。

## 中断・再開

「中断」は、不明な仕様に依存する実装・テスト・DB操作を止め、判断に必要な情報を残すことを意味する。停止理由が分かった時点で記録し、後続工程を完了扱いにしない。

- 仕様不足・矛盾：該当資料と箇所、不明点、影響する工程、判断が必要な質問を提示する。確認のための仮案を確定仕様として実装しない。
- 対象外のエラー：再現条件、原因の確認範囲、進行への影響を [Todo運用](../../../docs/todo/AGENTS.md) に従って記録する。編集範囲が明示的に限定される場合は許可された文書または最終回答へ残す。
- 環境・DB・権限の不足：失敗したコマンド、確認できた前提、未実行範囲、再開に必要な対応を記録する。認証情報や環境変数の値は出力しない。
- 作成・更新済みの成果物、検証結果、残件、再開する工程を報告する。テスト実行後の中断はレポートにも最新状態を残す。

ユーザーの回答や環境の修復後は、該当仕様・設計・コードの現状を再確認し、停止した工程から再開する。中断中のGit操作はリポジトリの指示に従い、未完了を完了として統合しない。

## 完了条件と報告

次のすべてを満たした場合だけ、API開発完了と報告する。

- 詳細設計、本番コード、テスト設計、テストコード・fixture、レポートが整合し、パス・関数・型・ケースの対応を確認できる。
- 必要な設計ケースと影響する回帰テストが成功し、必要な静的検査を通過している。対象外とする観点には理由があり、必須ケースのskip・未実行・未実装、未解決の失敗・未処理例外が残っていない。
- 実DBテストを行った場合はガード・スキーマ確認、cleanup・接続終了の結果が記録されている。モックの成功を実DB・外部送信の検証済みと扱っていない。
- 仕様確認待ち、進行を妨げる対象外エラー、環境不足が残っていない。残る場合は中断または部分実施として報告する。

完了時は `git diff --check` と変更範囲を確認し、`docs/log_memo/codex_log.md` に10行以内で記録する。コミット・developへの統合・作業ブランチ等の片付けは、ルート `AGENTS.md` の手順に従う。

最終回答では、実装したAPI、主要成果物へのリンク、実行したテスト・静的検査の結果、注意点を簡潔に伝える。未実行の確認を成功と報告しない。
