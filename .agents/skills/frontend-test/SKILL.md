# Frontend Test

## 目的・開始地点・範囲

ページ・コンポーネント・Hooks・API通信等のテストを、調査、設計、実装、実行、結果記録、許可範囲の修正、再検証まで進める。既存成果物を現行仕様と照合し、無条件に作り直さない。

- 設計書がなければ調査・設計から、設計済みなら実装から、修正IDやTodo指定なら該当原因の確認から開始する。
- 「設計のみ」「実行と修正案まで」等の工程制限を守る。テスト対象、本番修正対象、対象外、成果物を別々に整理する。テスト対象の指定を関連ページすべての変更許可とは解釈しない。
- このスキルの作成・編集依頼ではアプリのテスト作業を開始しない。

本文のパスはリポジトリルート基準、相対リンクはこのファイル基準。

## 修正の判断と停止境界

**本番コードの仕様が変更される修正は勝手に実行しない。レポートの修正案に記載して、その作業を終える。** スキルの呼び出しやテスト失敗は仕様変更の許可ではない。

- 確定仕様を満たしていない対象範囲内の実装不具合は、仕様を維持する修正として扱える。現行挙動の変化と確定仕様の変更を区別し、根拠を記録する。
- 表示契約、入力の許否・補完、検索、ページ補正、操作可否、二重送信抑止、認証・認可、状態遷移、API入出力、保存内容、副作用等の新設・変更は仕様変更となり得る。確定仕様を維持するか判断できない場合も実行せず修正案へ残す。
- テスト自身のモック・型・取得方法の誤りは修正する。期待値の変更は根拠と旧期待値を記録し、実測値に合わせるだけの変更はしない。仕様の矛盾を勝手に統一しない。
- 対象外コード、共有基盤、API、依存、DBをテストを通す目的で修正しない。migration・sync・ガード解除・環境の一括初期化を自動実行しない。
- 仕様変更が必要と判明したら、既存の証拠と実施状況をレポートへ確定し、依存する修正・検証を続けず終了する。新しい許可が得られた後、現状を読み直して再開する。

## 1. 調査・環境確認

1. git statusと適用規則を確認し、既存変更を保護して所定の作業ブランチを作成する。
2. 対象仕様、詳細設計、既存テスト・fixture・レポート・Todoを読む。Props、状態、Provider、SWRキーとcache更新、遷移、認証、API実ルート・JSON、日時・ID・nullable・数値文字列まで追跡する。
3. ユーザーの確定指示、仕様、API契約、設計、現行挙動を照合する。不一致を仕様未確定・設計の誤り・本番不具合・テスト不具合へ分類し、観測と期待を分ける。
4. Node・依存・認証・起動サービス・テストDB・schema等の前提を確認する。秘密値を出力しない。実行権限は環境の承認手順に従い、承認をDB変更許可と解釈しない。

## 2. 設計

成果物は配置規則に従う `client/test/docs/architecture/<領域>/<ページ等>.md`。

- 対象と根拠、責務・処理順、予定配置、fixture、実処理とモック、ケースID・優先度・条件・手順・期待結果、失敗時の後続未実行、実行順序・保留条件・完了条件を追跡可能にする。
- 単体は分岐・引数・境界、結合は親子・HTTP・cache・非同期順序、E2Eは実認証・API・DBの追加保証を主に担当する。全観点を全階層で重複実装しない。選ばない階層は理由を示す。
- 正常に加え空・null・型や数値の境界、失敗、再試行、競合・遅い応答・中断を責務に応じて選ぶ。新しい業務制約を発明しない。
- 見た目・操作感・フォーカス等は適用規則に従い人間観測へ分け、担当・環境・手順・期待・人間確認待ちを記載する。ブラウザー階層を理由に認可やDB整合性まで目視へ移さない。

## 3. テスト・fixture実装

- 最寄りのsrc/**/test、client/testの結合、独立testパッケージのE2E等、対象配置規則に従う。設計IDをテスト名へ引き継ぐ。
- 対象本体は実行し、依存境界だけ置換する。実JSONと加工fixtureを区別し、存在しないルートの成功handlerや暗黙変換で接続不整合を隠さない。
- 型アサーションで実データとの差を隠さず、wrapped構造、ID・日時・nullable等を忠実に再現する。型外入力の防御分岐は通常操作と区別する。
- DOM取得、user-event、非同期待機、SWR分離、時計・モック・環境変数・通信の後片付けは対象AGENTSに従う。snapshotだけで責務を保証しない。
- 独立して分担できる場合のみ規則に従いworktreeを分け、共有ファイルと統合・全体検査・レポートの担当を決める。

## 4. 実行・原因分類・再検証

1. 代表正常系と環境・接続契約を先行し、対象パスを指定して必要な単体・結合・E2Eを実行する。前提失敗中に後続を繰り返さず、独立ケースは継続可能か判断する。
2. 失敗をケース本体、import/収集/setup、権限・環境、仕様矛盾、対象外の既存診断へ分類する。ログ・実要求・assert到達位置から原因を確認する。
3. 仕様を変えない許可範囲の修正だけを行い、設計・テストとの整合を維持する。仕様変更が必要なら上記停止境界に従う。
4. 修正対象と関連回帰を再実行する。対象lint、本番型検査、テスト用型検査、必要なE2E型検査等を適用規則に従い確認する。対象診断なしと全体成功を分ける。
5. 新しい変更・失敗・未解決の疑問がなければ反復しない。環境障害に新しい根拠や対処がない場合は停止理由と再開条件を残す。

## 5. レポート・完了・再開

成果物は `client/test/docs/report/<領域>/<ページ等>.md`。修正案・再検証も同じ文書へ集約する。

- 冒頭に最新結果・今回の完了範囲・残件を示す。過去結果は日付・実行順付き履歴として維持し、現在の判定と混同しない。
- 設計IDとファイル・assert内容、環境・コマンド・モック境界、成功・失敗・未実行・未実装・中断、未処理例外、未到達の後続assertを記載する。
- 件数はランナーのJSON等から集計する。ID数・describe数・展開件数を区別し、再実行や複数IDを重複加算しない。setup停止を業務テスト失敗や成功に置き換えない。
- 修正IDごとに原因、再現条件、確認範囲、修正案、契約への影響、実装済み/提案のみ、再検証結果、残件・再開条件を記載する。
- 設計・実装・assert・リンクを照合し、必要な自動検証の成功と人間観測完了を別判定にする。未確認があるのに全体完了・全成功と報告しない。
- 作業ログ・Todo・Gitはルートと対象規則に従う。検証未完了や仕様判断待ちを完了として記録しない。

再開時は前回レポートと現在の差分を読み、仕様確定・環境復旧・許可範囲を確認して停止工程から再開する。既存の有効な成果物・ケースID・失敗履歴を維持する。
