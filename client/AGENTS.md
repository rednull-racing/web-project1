# Client Agent Instructions

## 対象

このファイルは `/client` 配下に適用する。
ルートの `AGENTS.md` を前提とし、フロントエンド固有の追加ルールを定義する。
対象ディレクトリに個別の `AGENTS.md` がある場合は、より作業対象に近いルールを優先する。

## 技術構成

- Next.js 16 / App Router / React 19
- TypeScript / ESM
- CSS Modules
- SWR / SWRInfinite
- NextAuth による既存の認証処理

## ディレクトリと責務

- `/client/src/app`: ページ、レイアウト、画面固有のコンポーネント・型・スタイル
- `/client/src/components`: 共通コンポーネント
- `/client/src/hooks`: 再利用するフック、SWR によるデータ取得処理
- `/client/src/lib`: 共通 API 通信、認証、ユーティリティ
- `/client/src/types`: 複数箇所で使用する型
- `/client/src/providers`: Context 等の Provider
- `/client/src/styles`、`/client/src/assets`: 共通スタイル、画像等のアセット
- `/client/test`: テスト設定・資料等。テストの配置と実行は対象の `AGENTS.md` に従う

既存の配置と命名を優先し、画面固有の処理を無理に共通化しない。

## コンポーネントとデータ取得

- Server Component を基本とし、状態管理やブラウザー API 等が必要な場合のみ `"use client"` を使用する
- サーバー専用処理を Client Component から import しない
- API 通信は `/client/src/lib/api/client.ts`、`server.ts` 等の既存の共通関数を優先し、認証要否と実行環境に応じて使い分ける
- クライアントでの取得・ページングは既存の SWR / SWRInfinite のパターンに合わせる
- 更新後は必要な SWR キャッシュを更新・再取得し、画面と API の状態を揃える
- CSS Modules の既存の命名と構成を維持する

## セキュリティ

- 認証が必要な画面・API 通信で、既存の認証処理を省略しない
- 表示制御や URL の ID だけで権限・所有権を保証せず、サーバー側の認可を前提とする
- パスワード、トークン、Cookie、個人情報をログへ出力しない
- シークレットをコードへ直書きせず、`NEXT_PUBLIC_` 環境変数やブラウザーへ渡す値に含めない
- ユーザー入力を未検証の HTML や遷移先 URL として使用せず、XSS や不正なリダイレクトを防ぐ

## 型

- `any` は原則使用せず、型アサーションは必要最小限にする
- API の実際のレスポンスに合わせて型を定義し、型アサーションだけで入力値やレスポンスを検証済みとみなさない
- `null` とプロパティ省略を区別し、必ず返る nullable 項目は `型 | null` とする
- 画面固有の型は近くの `types.ts` 等へ、共通の型は `/client/src/types` 等へ配置する

## エラー処理

- クライアントの API エラーは既存の `ApiError` とエラーコードの扱いに合わせる
- サーバー側の取得は既存の `redirect`、`notFound`、`error.tsx` 等の方針に合わせる
- エラーを握り潰さず、読み込み中・取得失敗・データなしを区別して表示する
- トーストやフォームのエラー表示は既存 UI に合わせ、内部エラーや機密情報を直接表示しない
- catch して同じエラーを投げ直すだけの処理や、デバッグ用の `console.log` を残さない

## import

- ESM 形式を使用し、型のみの依存には `import type` を使用する
- `@/` エイリアス、相対パス、拡張子、import 順は既存コードに合わせる
- 循環参照や、クライアントへのサーバー専用モジュールの混入を避ける

## status 管理

- API が定義する status と操作条件に合わせ、独自の状態値や遷移を追加しない
- 公開中・下書き・削除済み等に応じた表示と操作可否を確認する
- 業務データの status と、読み込み中・送信中等の UI 状態を区別する
- 送信中の二重操作を防ぎ、成功・失敗後の表示、キャッシュ、遷移先の整合性を確認する
- 非公開データの保護や status 遷移の最終判定はサーバー側で行う

## スコープ管理

- 依頼範囲以外の修正、リファクタリング、設計変更、ライブラリ追加を行わない
- 無関係なバグや改善点はその場で修正せず、`/docs/todo` の運用ルールに従って Todo を作成する

## 実装後の確認

変更範囲に応じて以下を実行する。

```bash
cd client
npm run lint
npm run typecheck
```

- 対象機能の関連テストを実行し、必要に応じて `npm run build` も確認する
- UI 変更では表示崩れ、画面幅、入力・操作、読み込み・エラー・空データ時の表示を確認する
- 実行できなかった項目や既存のエラーは、未確認の範囲と理由を報告する
- 作業後はルートのルールに従い、`/docs/log_memo/codex_log.md` に記録する
