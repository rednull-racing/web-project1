# Client Source Instructions

## 対象と基本方針

このファイルは `/client/src` 配下に適用する。
ルートと [client/AGENTS.md](../AGENTS.md) を前提とし、対象に近い `AGENTS.md` がある場合は、その詳細ルールに従う。
実装前に同じ種類の既存実装を確認し、配置・命名・責務の分け方を合わせる。

## ディレクトリ構成

```text
src/
├── app/                  # App Router、画面と機能固有の実装
│   ├── layout.tsx        # 共通レイアウト・Providerの組み込み
│   ├── page.tsx          # ルートページ
│   ├── error.tsx         # エラー表示
│   ├── global-error.tsx  # ルートレイアウトを含むエラー表示
│   ├── api/              # NextAuth等のRoute Handler
│   └── .../              # 機能・URLごとのページ、部品、型、スタイル
├── components/           # 複数画面で使うUI部品
├── hooks/                # 共通Hooks、SWRによる取得・更新
├── lib/                  # 認証、共通通信、表示整形等
│   └── api/              # client/server用の共通fetch関数、ApiError
├── providers/            # セッション等のContext Provider
├── types/                # 共通型・外部ライブラリの型拡張
├── config/               # サイト設定・定数
├── styles/               # 共通スタイル
├── assets/               # 画像等のアセット
└── middleware.ts         # 既存の認証・リダイレクト処理
```

- `app` 内では `page.tsx`、`layout.tsx` 等がURLと画面を接続し、画面固有の部品・`types.ts`・CSS Modulesは利用箇所の近くに置く
- 機能固有のAPI関数を分ける場合は、既存例の `app/item/draft/api/client.ts`・`server.ts` 等に合わせる
- 共通コンポーネントはPropsとイベントを通じて再利用する。機能専用の部品を配置統一のためだけに移動しない
- 単体テストは本番コードに最も近い `test/`、結合テスト・共通fixture・設計書・レポートは `client/test/` の規則に従う

## レイヤー構成

基本となる呼出しの流れは以下とする。すべての画面に中間層を新設する必要はない。

```text
ページ・レイアウト / 画面コンポーネント
    ↓
画面の操作・取得処理（Hooks / 機能固有API関数）
    ↓
共通API通信（lib/api、fetcher等）
    ↓
バックエンドAPI
```

| 役割 | 責務 |
| --- | --- |
| ページ・レイアウト | URLの値や初期データを受け取り、画面・部品を組み立てる |
| UIコンポーネント | 表示、入力、操作イベント、表示に必要な状態を扱う |
| Hooks | 再利用する状態・操作、SWRのキー・取得・キャッシュ更新を扱う |
| 機能固有API関数 | エンドポイント、HTTPメソッド、送信値、レスポンス型を定義する |
| 共通API通信 | 認証情報の付与、fetch、共通エラーの扱いを集約する |
| libのutility | 日時・文字列等の汎用処理を扱う |

業務上の認可、金額確定、status遷移の最終判定やDB操作はバックエンドの責務とする。

## レイヤー依存

- ページ・画面は共通UI、Hooks、機能固有API関数を利用できる。単純な取得では既存どおり共通API関数を直接利用してよい
- 機能固有API関数は共通通信へ依存し、JSXの描画、トースト、画面固有のstate操作を持ち込まない
- `components`・共通Hooks・共通utilityから、`app` 内の特定ページや画面固有の型へ依存しない。共有が必要な型は適切な共通配置を検討する
- 汎用utility・型・定数からページやProviderへ逆依存させず、循環参照を避ける
- Client Component・クライアント用Hooks/APIから、`lib/api/server.ts`、秘密情報、サーバー専用モジュールを読み込まない
- Server ComponentからClient Componentへ渡すPropsはシリアライズ可能な値とし、秘密情報を含めない
- Server Componentはクライアント用Hooksを実行しない。Providerは必要な範囲へ組み込み、`"use client"` を安易に上位へ広げない
- `app/api` のRoute Handlerとmiddlewareは既存の役割を維持し、バックエンドの業務ロジックやDBアクセスを追加しない

## ユーザー向け文章

- 画面、ボタン、フォーム、トースト、エラー等は、初めて使う人にも説明なしで伝わる日本語にする
- 案内文は「です・ます調」を基本とし、短く、親しみやすく、安心して操作できる表現にする。ボタンは「保存する」等、操作が分かる簡潔な文言にする
- 専門用語、内部のstatus名、エラーコード、開発者向けの処理説明をそのまま表示しない
- エラーでは何が起きたかと次にできる操作を伝え、ユーザーを責めたり不安をあおったりしない
- 「正常終了しました」より「保存しました」等の自然な表現を使う。入力案内は「メールアドレスを確認してください」等、対象を具体的に示す
- 既存画面と用語・表記を揃え、実際には保存できていない等、処理結果と異なる案内を表示しない

## 単体テストの共通ルール

配置とテスト階層は [テスト規則](../test/AGENTS.md)、設計は [設計書規則](../test/docs/architecture/AGENTS.md)、結果は [レポート規則](../test/docs/report/AGENTS.md) に従う。
明示された契約から期待値を定め、現行挙動の観測と仕様上の期待を区別する。テストを通すために仕様と異なる期待値へ変更したり、対象外の実装・設定を変更したりしない。

### 配置・記述

- TypeScript・ESMと既存のVitestを使用し、`src/**/test/` に `*.test.ts`・`*.test.tsx` を置く。importはclientの既存規則に合わせる
- DOMを使う対象はReact Testing Libraryとjsdom、DOMが不要な処理は必要に応じてNode環境で確認する
- `describe` は責務・観点で分け、テスト名にケースIDと日本語の条件・期待結果を含める。同じ構造の入力違いは `it.each` 等を使う
- 準備・対象の実行・検証が読み取れる構成にし、fixtureはテストごとに新しく作る。共有データの変更やランダム値に依存しない
- `any` を避け、既存型・型付きモックを使う。不正入力を直接渡すケースでは、通常の操作で到達する入力との違いを明記する

### 対象別の検証範囲

- UIはrole・ラベル・表示テキストから取得し、`user-event` でクリック・入力・キーボード操作を行う。内部stateやCSS Modulesの生成名に依存しない
- 表示条件、入力、コールバックの引数、操作不可、読み込み・空データ・失敗表示を対象の責務に応じて確認する。スナップショットだけで振る舞いの検証を済ませない
- Hooksは必要なProviderを用意して実処理を実行し、取得条件、更新、失敗、再実行等を確認する。SWRのキャッシュはケースごとに独立させる
- 機能固有API関数では共通通信をモックし、パス・メソッド・body・返却値・例外の扱いを確認する。共通通信自体のテストではfetchや認証の境界を制御する
- utilityは入力と結果、空値・null・数値や文字数等の境界、入力の不変性を必要に応じて確認する
- 正常系に加え、認証切れ、依存先の失敗、二重操作、遅い応答等から対象の責務に関係するケースを選ぶ。別の層だけが保証する条件を一律に課さない

### モック・非同期処理・独立性

- 検証対象そのものは実行し、依存先を `vi.mock`・`vi.fn`・`vi.spyOn` 等で置き換える。実ネットワークや実環境の認証情報へ接続しない
- HTTP境界を使うテストは既存のMSW設定に合わせ、未定義の対象APIへの通信を成功扱いにしない。対象をモックした結果だけを検証しない
- ケースごとにモックの履歴と実装を初期化し、SWRキャッシュ、DOM、イベント、タイマー、環境変数を後片付けする。既存の共通setupと役割を分担する
- 時刻・識別子は必要に応じて固定し、spy・fake timer・環境変数の差し替えは復元する
- Promiseと非同期アサーションは必ずawaitする。表示の更新は `findBy...`・`waitFor` 等で待ち、固定時間のsleepに依存しない
- 待機中・競合を確認する場合は制御可能なPromise等で順序を再現し、開始した処理をテスト終了までに解放・回収する
- `waitFor` の中でクリック等の副作用を繰り返さない。fake timerを使う場合はuser-eventのタイマー連携も設定する

### 境界と実行後の確認

- 非同期Server Component、実ルーティング、SSR・Hydration、レイアウト・ブラウザー互換性は既存のPlaywright規則に従う。単体テストに合わせて本番のComponent境界を変えない
- ナビゲーションをモックしたテストは遷移要求までの確認とし、実際の遷移やバックエンド・DBの動作まで検証済みと扱わない
- 単体と結合の範囲を区別し、複数の実コンポーネントやHTTP連携を検証する場合は `client/test/` の階層規則に従う

変更範囲に応じて `client` で以下を実行する。テストの型確認には既存のテスト用tsconfigも使う。

```bash
npm run test:unit -- src/<対象のtest>/
npm run lint
npm run typecheck
./node_modules/.bin/tsc --noEmit -p test/tsconfig.json
```

結果には実行コマンド、ケース・件数、モック範囲、既存エラー、未確認事項と理由を残す。
文書のみの変更ではリンク・参照先・実構成との対応・差分を確認し、テスト・lint・型検査の未実行を明記する。
