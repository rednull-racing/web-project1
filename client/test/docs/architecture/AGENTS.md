# テスト設計書の共通ルール

## 適用範囲・配置・参考資料

`client/test/docs/architecture` 配下に適用する。上位の AGENTS.md と [配置規則](../../AGENTS.md) に従う。

単体テスト～コンポーネント結合テスト～ページ結合テスト～E2Eテストまですべてこのディレクトリに1つのテスト設計書にまとめる。

コンポーネント結合テストのみ、ページ結合テストのみの場合も新規でテスト設計書を作成する。

対応する [レポート](../report/AGENTS.md)、詳細設計、対象コード、既存テスト・fixture などを調査する。パスは原則 `client/` あるいはE2Eなら `test/` 基準と明記し、リポジトリルート基準の参照は区別する。未作成のテストは「予定配置」とし、現配置や実装済みと混同しない。

ディレクトリ例：

- `/client/test/docs/architecture/item/itemDraftPage.md`
- `/client/test/docs/architecture/item/videoSection.md`
- `/client/test/docs/architecture/upload/uploadPage.md`

## 仕様の根拠と更新

規模に応じて章をまとめてよい。短い設計ではケースの箇条書きも可とし、次の情報を追跡できるようにする。

1. 対象・目的・仕様の根拠・作業範囲・対象外。
2. 関連ファイルと責務、処理順序、入力・業務判断・保存・応答の境界。
3. テストレベル、ファイル配置、実処理・モック・障害注入の範囲と保証の限界。
4. 標準 fixture、ケース別の変更点、共通アサーション。コピーや変換が多い場合は取得元と保存先の対応表。
5. ケース ID・レベル、条件・入力・手順、期待結果、異常時の停止位置と後続未実行。
6. 実装優先度、実行ディレクトリと対象コマンド、完了条件、未確認事項。

詳細設計にテスト観点がある場合は各観点とケース ID を対応付ける。「ケースを設計した」ことと「実装・実行して成功した」ことを区別する。

## 人間による目視観測の設計

- [人間による目視観測とCodexの分担](../../AGENTS.md#人間による目視観測とcodexの分担) に従い、画面から判断できる観点を選び、自動テストと人間による目視観測に分ける。ブラウザー検証やE2Eという階層だけで一律に目視へ移さない。
- レイアウト・画面幅、画像や動画の見え方、操作感、実画面遷移、キーボードとフォーカス、状態変化の見え方、ブラウザー差、体感性能は原則として人間が観測する。Codexはそれらを目的とするブラウザー操作やPlaywrightの作成・実行を行わず、明示依頼時のみ実施する。
- 人間の観測ケースは `O01` 等で区別し、担当「人間」、前提環境（ブラウザー・画面幅・アカウント・データ）、操作手順、目視で判断する期待結果、実施状況「人間確認待ち」を記載する。結果の記録先は対応するレポートとする。
- 入力境界、API契約、状態管理、競合、認証・認可、DB整合性など画面だけでは保証できない観点は必要な自動検証を残す。同じ観点の見た目と内部契約を分け、重複したブラウザー検証を計画しない。
- 完了条件はCodexの実装・自動検証の完了と、人間による目視観測の完了を区別する。人間の結果を受領するまでは未確認として残し、成功件数に含めない。
- 下記の対応表やPlaywright指定より、この分担を優先する。既存の自動テストは削除・弱体化しない。

## 敵対的なケースの検討

正常系の入力を少し変えるだけで終えず、**呼出し側が制約を破ろうとする場合や、依存先・実行順序が不利に働く場合を想定してケースを考える**。

敵対的な入力を理由に新しい業務制約を発明しない。期待する拒否・停止・不変条件は確定仕様に基づけ、仕様未確定なら観測ケースにする。

## ケース ID・優先度・検証境界

- ID は `N01`、`E01`、`V01` 等の観点と連番が分かる形式を使い、既存 ID を維持する。接頭辞とレベル記号は文書内で説明し、全機能で同じ意味と仮定しない。観測は `O01` 等で区別する。
- 同じ ID の複数条件を列挙し、実装時に独立したテストへ展開する。設計 ID 数、表の行数、`it.each` 展開後の件数を混同しない。
- 優先度は P0（基本契約・入力境界・所有権・原子性）、P1（helper 分岐・層間接続）、P2（重複・並行・観測）を目安とし、重要な競合は対象に応じて優先する。ケース ID の `P01` と優先度 `P0` は別物とする。

## 検証の重複と再実行を抑える設計

- 実行の共通方針は [実行量・トークン消費を抑える運用](../../AGENTS.md) に従う。設計書には対象固有の差分を記載し、共通規則を全文転記しない。
- 全階層を1つの設計書で扱うことは、全観点を全階層で重複実装する意味ではない。観点ごとに主に保証する階層を決め、上位階層では接続・実認証・永続化など追加される保証に絞る。省略する階層は根拠と代替検証先を示す。
- 共通フォーム等のモード違いは共通契約と差分を分け、代表モードの網羅ケースと各モードの差分ケースを対応付ける。認可や異なる処理経路を代表ケースだけで保証したとみなさない。
- 環境確認と代表正常系を先行する順序を設計する。ケース間の前提、失敗時に保留する依存ケース、継続できる独立ケース、再開条件を明示する。同じ保存APIが失敗している間に後続の転送障害ケースを繰り返す等の実行を避ける。
- 並列作業では環境確認・全体検査・統合集計の担当を決め、各担当の検証範囲を分ける。変更時の再実行範囲と統合後の確認を計画し、小変更のたびに全階層を再実行する計画にしない。
- 結果・失敗/修正案・残件は対応レポートへ集約する。共通の人間観測規則や実行手順は参照し、対象固有の前提・手順・期待結果とケースIDの追跡性を残す。集計の機械生成を利用し、同じ情報の手動転記を減らす。

## 修正案・追加設計・確認

- 修正案と実行結果の本体は [統合レポート](../report/AGENTS.md) にまとめる。設計書には現行契約と追加ケースを反映し、実行履歴を重複転記しない。
- 修正 ID（`F1` 等）と元ケースを対応付け、追加ケースは `AF-ID01`、`AF-DB01` 等、既存文書に合う ID を付ける。単なる未実施部分の補完と契約変更を区別し、全追加ケースへ機械的に新 ID を振り直さない。
- 既存ケースの維持・期待値変更・責務移行を示す。旧挙動の観測は修正実装後に新契約へ移し、根拠と旧結果をレポートに残す。無関係な assert を弱めない。
- 対象 Vitest、`npm run lint`、`npm run typecheck`、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` の計画を記載する。本番型検査とテスト型検査の対象差、通常 lint 対象外 TS の追加検査を確認し、共有設定を独断変更しない。
- 最後に相対リンク・パス・ケース対応・契約の優先関係・完了条件・差分を確認する。文書だけの変更ではテスト未実行と報告する。対象外の問題は `/docs/todo/AGENTS.md` に従い、編集範囲が明示的に限定される場合は許可された文書または最終回答へ残す。
