# テストレポートの共通ルール

## 適用範囲・配置・参照

`client/test/docs/architecture` 配下に適用する。上位の AGENTS.md と [配置規則](../../AGENTS.md) に従う。

[設計書規則](../architecture/AGENTS.md)、対応する設計書、詳細設計、現行コード、実際のテスト・fixture と実行結果を照合する。コードパスの基準（原則 `client/`）を明記し、移動後の配置と過去のコマンドを区別する。

## 冒頭の最新結果と履歴

- 冒頭に実行日・対象・最新結果・完了範囲・残る問題を記載する。最新の詳細を末尾へ追記する構成も可とし、冒頭からその節へリンクする。再検証のたびに最新要約も更新する。
- 「今回実行した範囲」と「以前確認したが今回再実行していない範囲」を分ける。部分的な修正・回帰成功を機能全体や全設計の再検証完了としない。
- 過去の件数・失敗・未実施・提案は日付付きの履歴として残す。最新節と矛盾する旧記述は履歴であると明示し、解消した F 番号や更新したケースの現在の状態を示す。
- 同日の複数実行は修正内容・対象・実行順で識別する。旧配置の履歴を残す場合は現配置表へ参照を結ぶ。

## 報告に必要な情報

規模に応じて見出しや表をまとめてよい。次を追跡できるように記録する。

1. 作業・実行日、依頼範囲、変更したファイル、実装した内容と対象外。
2. テストファイルごとの結果と全体集計。単体・DB 非接続結合・実 DB・既存回帰を区別する。
3. 実行ディレクトリ、再現できる対象コマンド、ランナー出力・JSON 等の集計根拠、静的検査の成否。
4. 実処理・モック・障害注入の境界と確認できる範囲・確認できない範囲。
5. 設計ケース ID とテストファイル・確認内容・判定・残る範囲の対応。複数 ID をまとめる場合も対応を追えるようにする。
6. 失敗・観測の入力、再現手順、実際の結果、原因の確認範囲、修正案と未達事項。

ケース ID がテスト名に存在するだけで完了とせず、assertion が設計内容を確認しているか照合する。敵対的ケースも、拒否結果だけでなく後続未実行・情報非公開・行の不変など設計した条件まで照合する。複数条件の一部や一部レベルだけを実施した場合は、その範囲を明記する。

## 件数・判定・証拠

- 件数は今回の実ランナー出力・JSON から集計する。設計 ID 数・表の行数・`it.each` 展開後のテスト数を別に扱い、複数 ID の重複対応を加算しない。
- ファイル数は実ファイルの結果から数える。describe 等を含む suite 集計をファイル数とみなさず、assertion failure が複数あっても一つのテストを複数件にしない。
- 成功・失敗・skip/pending・todo と未処理例外を記載する。収集失敗、import/setup 失敗、ケース本体の失敗を区別する。setup 失敗でランナーが skipped/pending と表示した場合は本体未実行であることも明記する。
- 設計上の「成功」「失敗」「一部実施」「未実装」「未実行」「対象外」「観測」を区別する。未作成ケースをランナーの skip 件数へ混ぜない。観測テストの成功は望ましい仕様や不具合解消を意味しない。
- 再実行・対象を絞った確認・既存回帰を重複加算しない。異なる実行を合算する場合は対象が重ならないことと各根拠を示す。途中の失敗と最終集計を分ける。
- カバレッジは取得した場合だけ対象と行・分岐の結果、未実行部分の理由を記載する。未取得も明記し、件数や高い割合だけで完了としない。
- 一時 JSON・ログは集計元としてパスを示してよいが、一時成果物であることを明示し、重要な結果・手順・未達を本文にも残す。認証情報・トークン・env 内容・接続 URL 全体を転記しない。

## 修正案・追加テスト・再検証

- 修正案は観測結果と元ケース ID を根拠に、修正 ID（`F1` 等）、対象、原因、修正前の再現条件、修正方針、修正後の契約、対象外を記載する。原因未特定・仕様未確定の事項を修正必須と断定しない。
- 提案のみ・実装済み・検証済み・残件ありを区別する。コード照合・報告だけの作業を実装修正とせず、報告作成の依頼から本番・テスト・設定・DB の修正許可を推測しない。
- 追加ケースは `AF-ID01`、`AF-DB01` 等、既存文書と整合する ID で元ケース・レベル・入力/手順・期待結果へ対応付ける。未実施の補完は元 ID を活かし、契約変更による期待値更新と分ける。
- 既存ケースの維持・期待値変更・責務移行を記載する。旧不具合の観測は修正実装後に新契約へ移行し、設計書にも根拠を反映する。無関係な assert の緩和や、失敗を隠す削除・skip/todo 化をしない。
- 修正後は関連回帰と必要な実 DB・競合ケースを再実行し、変更・ケース対応・結果・未達・完了範囲を同じ文書へ追記する。再修正では前案から変えた理由も示す。
- 共通機能として独立した設計・レポートを作る場合は、その機能側に本体を集約する。起点のレポートには元の F/ケース ID、解消状況、回帰結果、独立文書へのリンクを残し、全文複製しない。
- 対象外の問題は `/docs/todo/AGENTS.md` に従う。編集範囲が明示的に限定される場合は許可されたレポートまたは最終回答へ残し、範囲外を編集しない。

## 静的検査・文書更新の確認

- `client/` での対象 Vitest、`npm run lint`、`npm run typecheck`、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` の対象・成否を記録する。本番 typecheck は `src/**/test` を除外し、テスト用 tsconfig が単体・結合を含むことを区別する。
- 通常 lint の対象外 TS は既存 ESLint・typescript-eslint による追加検査の対象・方法・結果を示す。検査を通すために共有設定を独断変更しない。
- 対象ファイルに診断がないことと検査全体の成功を区別し、失敗コマンド・原因・今回の変更との関係を示す。HTTP 待受制限と DB 接続制限も分け、再実行の有無を記載する。
- 文書だけの変更はリンク・パス・ケース対応・最新要約と履歴の整合・差分を確認し、テスト未実行と明記する。過去の成功を今回の結果として再掲しない。
