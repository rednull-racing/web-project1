# バックエンド詳細設計の共通ルール

## 適用範囲と目的

- `docs/design/backend/detail` 配下の詳細設計書の作成・更新に適用する。
- API契約、処理順序、DB操作、失敗時・競合時の動作を、実装とテストの担当者が判断できる粒度で記述する。
- 上位のAGENTS.mdと対象層の規約を守り、詳細設計で認証・認可や責務分離を緩和しない。設計の依頼だけで本番コード・テスト・設定・DB・既存migrationを変更しない。

## 開発手順の参照

- 作業開始前に [API開発スキル](../../../../.agents/skills/api-development/SKILL.md) を読み、適用範囲と工程別の手順・中断条件・完了条件を確認する。
- 詳細設計のみの依頼では該当工程を参照し、実行範囲はユーザーが依頼した工程に限定する。

## 作業前に確認するもの

1. 関連する基本設計と、同じ機能領域の既存詳細設計。
2. [serverの規則](../../../../server/AGENTS.md)、対象ディレクトリのAGENTS.md、[コーディング規約](../../../codingRule/backend/AGENTS.md)と対象層の規約。
3. route・middleware・validator・controller・usecase・service・型と、実際のimport/export・Router登録。
4. 関連Model・associate・migration、反映済みDBの根拠、既存テスト・fixture。
5. 対応する[テスト設計書](../../../../server/test/docs/architecture/AGENTS.md)、[統合レポート](../../../../server/test/docs/report/AGENTS.md)、関連Todoと完了履歴。

- DB反映前はModel、反映後はDBを正とする上位ルールに従う。Model・migrationの存在だけで適用済みと判断せず、DB未確認ならその範囲を明記する。設計作成のために無断でmigrationやsyncを実行しない。
- 過去の設計の「新規予定」「未実装」「DB不一致」を現在の状態とみなさず、現行コードと最新レポートを照合する。旧カラム・旧パス・廃止APIを新設計へ転記しない。
- 明示された仕様・変更指示、現行実装、観測結果、提案、未決定事項を区別する。不一致は根拠とともに記録し、設計か実装のどちらかを推測で正として変更しない。
- 更新時は確認日・仕様変更の根拠・更新範囲を示す。履歴を残す場合は、冒頭で優先する契約と旧記述の範囲を明確にし、確定済みの事項を未決定欄へ残さない。
- 対象外の問題は[Todo運用](../../../todo/AGENTS.md)に従う。編集範囲が明示的に限定される場合は、許可された文書または最終回答へ残す。

## 配置・参考例・章構成

機能領域のディレクトリに処理名のMarkdownを置き、既存の命名を維持する。タイトルは `# <処理名> 詳細設計`、冒頭には基本設計への相対リンクと、必要な参照実装・更新時点を記載する。本文は日本語、識別子・カラム名は実定義に合わせる。

参考例は目的別に選び、機能固有の値・状態遷移・未確定事項を雛形として複製しない。

| 参考例 | 主な観点 |
| --- | --- |
| [createItemEditingDraft](itemEditing/createItemEditingDraft.md) | 下書きから編集行への移行、コピー元の消費、取得・作成・削除の原子性 |
| [createItemEditingCopy](itemEditing/createItemEditingCopy.md) | 元商品を保持するコピー、関連値の展開、在庫変換、繰返し生成の契約 |
| [deleteItemDraft](itemDraft/deleteItemDraft.md) | bodyなしのDELETE、所有者限定の物理削除、非対象データの保持 |
| [createItem](items/createItem.md) | 複数テーブル生成、関連ID、算出値、保存済みデータの前提検証、commit後通知 |

既存の次の章順を維持する。該当しない項目は理由を示し、機能に存在しない処理を章埋めのために追加しない。第9章は未決定事項がある場合に設ける。

| 章 | 記載内容 |
| --- | --- |
| 1. 概要 | 目的、入力元・出力先、成功・失敗後の状態、対象外 |
| 2. API仕様 | HTTP契約、担当ファイル・関数・型、入力検証 |
| 3. 認証・認可 | 認証情報の取得元、所有者・操作権限・状態条件 |
| 4. 処理フロー | 番号付き手順とMermaid図、分岐・停止・応答の位置 |
| 5. DB操作仕様 | 参照・作成・更新・削除、コピー・変換・算出・関連の対応 |
| 6. トランザクション設計 | 境界、参加処理、失敗時の状態、ロック・競合・再送 |
| 7. エラー設計 | 発生条件、HTTP、公開コード・応答、内部例外との境界 |
| 8. テスト設計 | 正常・異常・並行・境界・条件分岐・状態遷移と期待結果 |
| 9. 未決定事項 | 未確定の条件・値・応答、必要な判断とその影響範囲 |

## API仕様と責務分離

- Method、Endpoint、認証・認可、Content-Type、レート制限を明記する。Router内の相対パスと実HTTPの共通prefixを区別し、bodyなしのリクエストとJSONレスポンスのContent-Typeを混同しない。
- body・params・queryと認証情報の採用元、項目名・型・必須/任意・nullable・許容範囲・不正時の扱いを記載する。数値へのcoerce、未知キー除去、検証済み値の格納先を確認する。DB型の上限と、そのAPIが実際に検証する上限は分ける。
- bodyがある場合はJSON例、ない場合はメソッド・URL例で示す。成功statusと公開レスポンスのJSON例を記載し、応答がcommit完了を待つかも示す。
- route、認証・制限・検証middleware、schema・型、controller、usecase、serviceのファイル・関数を記載する。パスの基準はリポジトリまたは `server/src` 等と明示し、既存・新規予定・変更・廃止を区別する。
- routeは接続、controllerは検証済み入力・認証情報の引渡しと応答、usecaseは業務判定・変換・transaction、serviceはDBアクセスを担当する。外部通信は対象の規約に沿うinfra・utility等の境界を示す。
- routeの三行コメントを記載する場合は、メソッド・パス、summary、pageを対象規約と一致させる。旧API置換時はURL維持・変更・廃止と既存呼出しへの影響を示す。

## 認証・認可・入力と処理順序

- 認証済みuserIdの取得元、認可対象のModel・所有者カラム、検索条件を明記する。body・URLのIDだけで所有権を判断せず、所有者条件付き検索と取得後の判定を区別する。
- 不存在・他人・操作不可status・論理削除・消費済みの条件と応答を対象ごとに定義する。statusや削除列がないModelへ条件を発明しない。関連再取得がある場合も認可条件を確認する。
- parser→認証→レート制限→schema→controller→transaction等の実際の接続順と停止位置を示す。parserが認証より前で拒否する場合、Router側の通常body検証と分ける。複数不備でどの応答が先になるかも確認する。
- レート制限はキー・適用単位、期間・回数、超過status・応答/ヘッダー、失敗要求の消費、窓終了後の再開を記載する。不正JSON・未認証・schema拒否・業務失敗を一律に同じ計上としない。
- 手順とMermaid図で、前提検証・DB参照/更新・commit/rollback・副作用・応答の順序を揃える。開始前の拒否にrollbackを描かず、失敗時の停止とエラー処理への接続も示す。

## DB操作・データ対応・算出値

- テーブル、取得列・関連、where・status・所有者条件、作成・更新・削除の件数と対象を示す。親・任意関連の欠落と、必須参照がない不整合を区別する。
- コピーは「共通カラム」だけで済ませず、元と先のカラムを列挙する。同名コピー、名前変更、固定値、初期化、算出、対象外を表やコード例で区別する。
- ID・所有者・日時・管理値は、新規採番、認証ID使用、引継ぎ、除外を明示する。関連行を新規生成するのか、既存FKを保持するのか、関連値を行内へ展開するのかを分け、FKの保存側と参照先をModel・associateに照合する。
- コピー元を保持する処理、削除して消費する処理、同じ行の更新、物理削除を区別する。既存商品・他人の行・下書き・メディア等の非対象を明記し、URL文字列のコピーと実S3オブジェクトの複製・削除を混同しない。
- JSONB・在庫変換は対象階層、許容する欠落/null/空配列、不正構造、数値条件、初期化項目を示す。HTTP入力の拒否と保存済み不整合の拒否を分け、元オブジェクトの非破壊・別参照・順序や追加キーの保持も契約に応じて明記する。
- 集計・検索文字列・並び順等は、参照元、取得タイミング、where、算式・係数・閾値、正規化、fallbackを記載する。必須値の欠落をfallbackで隠さず、作成前集計と作成後集計、対象自身を含めるかを区別する。

## トランザクション・排他・再送

- usecaseの開始・終了位置と、同一transactionを渡す取得・集計・作成・更新・削除の各serviceを列挙する。callback終了と外側transaction Promiseの完了を区別し、成功応答の確定位置を示す。
- 途中失敗時に戻る元行・消える作成行・関連行と非対象行を示す。rollbackによる取消しと、別transactionで行う削除補償を混同しない。部分成功や孤立行を残さない範囲を明確にする。
- callback内障害・実SQL失敗・開始失敗・commit不成立・実COMMIT応答喪失を分ける。成否不明の通信断を「必ずrollback成功」と断定せず、commit後のHTTP送信失敗で確定済みDBを復元できるとしない。
- transaction開始だけで排他成立としない。ロックする行・種別・取得時点・保持期間、二段階取得と関連再取得、ロックしない関連・集計元を明記する。分離レベルに依存する再評価はその前提を示す。
- 先行の更新・削除・所有者変更と、後続の待機→ロック後再取得→存在/所有者/状態の再判定を記述する。先行commitとrollbackの両方、同じ対象と別対象、逐次再送と失敗後再試行を分ける。
- 元行の消費後は後続404とする処理と、元行を保持して要求ごとに新規行を作る処理を区別する。ロックや逐次成功だけを根拠に、一意性・冪等性・全参照の厳密な直列化を保証しない。

## 通知・失敗許容の副作用がある場合

- 必須DB処理と通知・外部通信等の副作用を分け、開始時点、引数、参照する新規ID、transactionの有無、完了待ちの要否を示す。
- commit後の非待機処理では、DB成功後だけ開始すること、失敗の捕捉、成功応答や確定済みDBへの影響を明記する。通知の保存・送信・再送を成功条件に含むかを区別する。
- 意図的な失敗許容をテスト都合でawaitへ変更せず、再送時の通知重複や自動再試行を未確定のまま保証しない。副作用がない機能へ形式だけの通知処理を追加しない。

## エラー・テスト・未決定事項

- 発生条件、内部のAppError/元例外、公開HTTP・コード・JSON・必要ヘッダーを表で対応付ける。認証・レート制限の応答をAppError形式へ一律変更せず、予期しない例外の内部情報を公開しない。
- request/schemaの不正、保存済みデータの不整合、Model validation、実DB制約を区別する。既存コードの利用・新規案・未確定値が分かるようにし、コード例を確定値と混同しない。
- 第8章は実装を確認する観点と期待結果を記載し、[テスト設計書の規則](../../../../server/test/docs/architecture/AGENTS.md)へつなぐ。敵対的な所有者偽装・破損構造・複数不備・途中失敗・再送・競合も対象の責務に沿って検討する。拒否だけでなく後続未実行・非対象不変も示す。
- 正常・異常・並行・境界・条件分岐・状態遷移を扱い、コピー内容・生成件数・保持/消費・rollback・再試行を検証可能にする。任意値の片側正常による不正の見逃し、深い階層や後方要素、上下限の前後も契約に応じて検討する。
- 単体の引渡し・変換・待機、HTTPの接続・公開応答、実DBの保存・制約・ロックを分ける。実ロック待機を観測する競合ケースと、モックの順序確認を同じ保証としない。詳細ケースIDはテスト設計へ対応付け、件数や実行履歴を全文複製しない。
- 設計した観点は実行済み結果ではない。実行結果・修正履歴は統合レポートへ参照を結ぶ。確定できない条件・値・応答・DB反映状況は第9章へまとめ、本文や図で確定扱いにしない。

## 完了前の確認

- API、認証・認可、手順、Mermaid図、DB対応、transaction、副作用、エラー、テストの条件・順序・結果を照合する。
- 基本設計、現行のModel/DB根拠、規約、テスト設計・最新レポートと整合させ、パス・リンク・関数・型・予定/実装済み区分を確認する。
- 特定機能の数値・状態遷移・過去の不具合を共通仕様へ広げず、無関係な設計書や本番コードを変更していないことを確認する。
- `git diff --check` を確認し、作業ログは `docs/log_memo/codex_log.md` へ10行以内で記録する。文書のみの変更ではテスト・lint・型検査を再実行していないと報告する。
