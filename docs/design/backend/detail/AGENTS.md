# バックエンド詳細設計の共通ルール

## 適用範囲と目的

- このファイルは `docs/design/backend/detail` 配下の詳細設計書を作成・更新する作業に適用する。
- 詳細設計は、API契約、処理順序、DB操作、失敗時・競合時の動作を、実装とテストの担当者が判断できる粒度で記述する。
- 上位の `AGENTS.md` と対象層の規約を守り、詳細設計でセキュリティや責務分離の要件を緩和しない。

## 作業前に確認するもの

1. 関連する基本設計と、同じ機能領域の既存詳細設計
2. 対象となる `server` 配下の `AGENTS.md` と `docs/codingRule/backend` の該当規約
3. 関連するroute・middleware・validator・controller・usecase・service・型定義
4. 関連モデル、リレーション、マイグレーションと既存テスト

- DB反映前はモデル定義、反映後はDBを正とする上位ルールに従う。モデルだけでDB反映済みと判断しない。
- 設計と実装の差異を発見した場合は、確認した事実と未決定事項を区別し、どちらかを推測で正として仕様を変更しない。
- 詳細設計の依頼だけで実装・DB・既存マイグレーションを変更しない。範囲外の問題は `docs/todo/AGENTS.md` に従って記録する。

## ファイル構成と記述形式

- 既存の `itemEditing/createItemEditingCopy.md`、`itemEditing/createItemEditingDraft.md` を構成の参考にする。
- 機能領域ごとのディレクトリに、処理名に対応するMarkdownファイルを置く。既存の命名・配置を優先する。
- タイトルは `# <処理名> 詳細設計` とし、冒頭に関連する基本設計への相対リンクを記載する。
- 本文は日本語で記述し、識別子・テーブル名・カラム名は実際の定義に合わせる。
- 次の章をこの順序で設ける。対象外の項目は、その旨と理由を記載する。

| 章 | 記載内容 |
| --- | --- |
| 1. 概要 | 目的、入力元・出力先、成功時・失敗時の状態 |
| 2. API仕様 | HTTP契約、担当ファイル・関数・型、入力検証 |
| 3. 認証・認可 | 認証情報の取得元、所有権・操作権限の判定 |
| 4. 処理フロー | 実行順序と分岐、Mermaidによる処理フロー図 |
| 5. DB操作仕様 | 参照・作成・更新・削除の対象と条件、データ対応 |
| 6. トランザクション設計 | トランザクション境界、失敗時の状態、排他制御 |
| 7. エラー設計 | 発生条件、HTTPステータス、既存規約に沿ったエラーコード |
| 8. テスト設計 | 正常系・異常系・並行処理・境界値・条件分岐・状態遷移 |
| 9. 未決定事項 | 未確定の仕様と確認が必要な点。未決定事項がある場合に設ける |

## API仕様と責務分離

- Method、Endpoint、認証・認可、Content-Type、レート制限の有無を明記する。
- 入力はbody・params・queryなどの取得元を区別し、項目名、型、必須／任意、許容範囲、不正時の扱いを記載する。IDの上限は対象のDB型も確認する。
- リクエスト・レスポンス例はJSONコードブロックで示し、成功時のHTTPステータスと返却項目を明記する。
- レスポンス形式とエラー形式は既存の共通API規約に合わせる。未確定の例を確定済みの契約として扱わない。
- 担当するroute、認証・レート制限・検証middleware、validator、controller、usecase、service、関連型のファイル名と関数・型名を記載する。既存利用と新規作成を区別する。
- パスはリポジトリ基準か `server/src` 基準かを明示し、既存の参照先・識別子を確認する。新規予定のものは予定と分かるようにする。
- route・controllerに業務ロジックを置かず、usecaseが業務処理を、serviceがDBアクセス・外部通信を担う設計にする。
- routeの三行コメントを記載する場合は、HTTPメソッド・パス、summary、pageを該当規約と一致させる。

## 認証・認可と処理順序

- 認証済みユーザーIDの取得元と、所有者を照合する対象モデル・カラムを明記する。URLやbodyのIDだけで所有権を判断しない。
- 存在しない場合、所有者でない場合、操作対象のstatusでない場合、論理削除済みの場合の取得条件と応答を定義する。
- レート制限を設ける場合は、適用単位、期間、回数、超過時の応答、不正入力も回数に含むかを記載する。既存2機能の具体値を全APIへ一律に適用しない。
- 認証・レート制限・入力検証とトランザクション開始の順序を明示する。既存2機能では認証→レート制限→入力検証→トランザクション開始の順序を維持する。
- 番号付きの処理手順とMermaid図で、判定条件、DB操作、コミット・ロールバック、成功・エラー応答を一致させる。

## DB操作とデータの引き継ぎ

- 参照・作成・更新・削除するテーブル、関連データ、where条件を明記する。statusや論理削除条件が必要な取得では、関連データの再取得も含めて条件を確認する。
- コピー処理ではコピー元とコピー先のカラムを列挙し、同名コピー、名前変更、固定値、初期化、変換、コピー対象外を区別する。「共通カラムをコピーする」だけで済ませない。
- ID、所有者ID、外部キー、日時、管理用カラムについて、新規生成・認証情報の使用・引き継ぎ・除外の扱いを明記する。
- JSON属性や在庫などを変換する場合は、対象階層、変換規則、欠落・null・不正な保存済み値の扱いを記載する。入力検証エラーと保存済みデータの不整合を区別する。
- コピー元を保持するか削除するか、対象外のデータを変更しないことを明記する。下書きからの移行と販売中商品のコピーを同じ状態遷移として扱わない。

## トランザクション・排他制御

- トランザクションの開始・終了位置と、同一transactionを渡す取得・書き込み・削除の各serviceを明記する。
- 成功時は必要なDB操作がすべて成功してからコミットし、失敗時はロールバック後に残るデータ・残らないデータを明記する。
- ロールバックによる取り消しと、別途実行する削除・補償処理を区別する。
- トランザクション開始だけで排他制御が成立すると記載しない。行ロックを使う場合は対象、ロック種別、取得時点、保持期間を記載する。
- ロック後のデータに基づく存在・所有者・状態の再判定と、先行処理のコミット／ロールバック後に待機中の後続処理がどう動くかを定義する。
- 同一対象への同時リクエスト、成功後の再リクエスト、失敗後の再試行、別処理による更新・削除との競合を区別する。
- 重複生成の許可／禁止は機能ごとに明記する。ロックを使用することだけを根拠に重複生成を禁止しない。

## エラー・テスト・未決定事項

- エラーは発生条件・HTTPステータス・エラーコードの対応表にまとめ、既存の `AppError` とmiddlewareの規約に合わせる。コード例と確定値を区別する。
- テスト設計には操作・条件と期待結果を記載し、API応答だけでなくDBの生成件数、コピー内容、保持・削除、途中データの残存も確認できるようにする。
- 正常系・異常系に加え、IDやレート制限の境界、任意項目・空値、各DB操作の失敗、競合後の再判定、再リクエスト・再試行を対象仕様に沿って記載する。
- 認証・認可・入力・レート制限で拒否された場合は、後続処理の停止とDB状態への影響も確認項目に含める。
- 詳細設計のテスト項目は、実行済みの結果として記載しない。
- 未確定の条件・値・応答は未決定事項にまとめ、本文や図で確定済みとして断定しない。既存文書に曖昧な記載があっても推測で採用しない。

## 完了前の確認

- API仕様、認証・認可、処理手順、図、DB操作、トランザクション、エラー、テストの条件と結果が一致していること。
- 基本設計、モデル・DB制約、既存規約との整合性を確認し、参照リンク・パス・関数名・型名が正しいこと。
- 特定機能の値や状態遷移を、根拠なく他機能の共通仕様に広げていないこと。
- 変更範囲と `git diff --check` を確認し、上位ルールに従って `docs/log_memo/codex_log.md` に10行以内で作業を報告すること。
