# Todo運用

作業中に今回のタスクと無関係な問題を見つけた場合は、
その場では修正せずTodoとして記録する。

現在依頼されているタスク以外は変更しない。

適切な優先度フォルダに、新しいTodoファイルを作成する。

## 優先順位

- P0-critical
- P1-bug
- P2-refactor
- P3-techdebt
- P4-idea

## エージェントが作業前に読むもの

- Todoを調査・実装・更新する前に、対象のTodoファイルを全文読む。タイトルや検索結果の抜粋だけで作業を始めない。
- 依頼でTodoが指定されている場合は、そのファイルを起点にする。指定がない場合も、今回の対象に関係する未完了Todoと `done/` の履歴を検索し、重複した記録や対応済みの問題がないか確認する。無関係なTodoまで実装範囲を広げない。
- 対象ファイル・参照ファイルとして挙げられたコード、設計書、テスト、レポートと、作業対象に適用されるAGENTS.mdを読む。移動前のパスは現在の配置を確認し、古いimport先や削除済みカラムを前提にしない。
- 完了・結果・追記の日付と内容を確認し、初回調査、提案、確定仕様、実装済み、検証済み、残件を分ける。優先度フォルダにあることだけで未修正と判断せず、現行コードと最新レポートを照合する。
- Todoの修正方針は記録時点の案である。今回のユーザー指示と現行の契約を優先し、仕様未確定・原因未確認の点は推測で実装しない。Todoを読んだことや優先度が高いことを、依頼範囲外の修正許可と解釈しない。

## Todoの書き方

Todoは、人間とエージェントがファイル全体を読んで、そのまま調査・実装へ進めるMarkdownとして書く。問題、根拠、対応内容、変更範囲を本文にまとめる。

エージェントには対象Todoのパスを示して全文を読ませる。一部分のコピーを前提とした「実装プロンプト」や「Codexへそのまま渡せる実装プロンプト」の項目は作成しない。

新規作成前に関連する未完了Todoと `done/` を確認する。同じ問題の追記なら既存Todoを更新し、別の原因・対応範囲なら分けて関連先を示す。

## Todoに記載する内容

- タイトル
- 問題の概要
- 原因
- 修正方針
- 対象ファイル（必要な場合）
- 参照すべきファイル（必要な場合）
- 実装内容
- 実装時の注意事項

必要に応じて、発見日、再現手順・入力、実際の結果と期待結果、確認コマンド、完了条件を添える。確認済みの原因と仮説、今回の対象と対象外を区別し、未実行のテストを成功済みと書かない。見出しは既存の「問題と原因」「対象・参照」などへまとめてもよい。

## 完了時の記録と移動

- 対応と必要な確認を終えたTodoは、**元の優先度フォルダから `docs/todo/done/` へ移動する**。完了と書くだけで未完了の一覧へ残さない。
- 移動前に冒頭または結果欄へ、完了日、対応内容、確認結果、関連レポートと残る対象外事項を記録する。初回の問題・依頼内容は履歴として残し、現在も未解決のように読める記述には過去の記録であることを示す。
- 一部対応・方針提案だけ・必要な検証が未実施の場合は、残件と理由を記載して元の優先度フォルダへ残す。修正不要や対応しない方針が確定して終了する場合は、その判断理由を記録して `done/` へ移動する。
- ファイル名は原則維持し、コピーではなく移動する。移動先に同名ファイルがある場合は内容を確認し、既存の履歴を上書きしない。
- 移動によって相対リンクや参照元が切れないか確認し、今回の作業に関係する参照を更新する。`done/` は対応履歴として読み、新しい実装依頼や未完了Todoとして扱わない。

## 良い文章

AIだけでなく、開発者にとっても読みやすく、数週間後の人間の開発者が読んでも内容をすぐに理解できる文章にする。

- 1項目を短くする
- 「何が問題か」と「何をするか」が分かるようにする
- 必要な技術用語は使うが、説明文を過度に形式化しない
- 「～する必要がある」「～を検討する」などの堅い表現は避ける
- 可能なら「問題 → 対応」の順番で書く
- AIへの命令文でもあるが、人間が残した開発メモとして書く
- 数週間後にこのTODOだけを読んでも、なぜ追加されたのかわかるようにする

### 悪い例

- 認証処理における責務分離の観点から middleware 構成を再検討する必要がある。

### 良い例

- 認証処理が middleware に寄りすぎている。どこまで middleware でやるか整理する。
