## このディレクトリについて

server/src はバックエンドのソースコードを配置するディレクトリです。

各ディレクトリは責務を明確に分離してください。

```
src/
├── app.ts                 # アプリケーション初期化
├── routes/                # URL・HTTPメソッド・middleware・Controller呼び出し
├── controllers/           # HTTPリクエスト・レスポンス
├── usecases/              # 業務ロジック
├── services/              # DBアクセス
├── models/                # Sequelize Model定義
├── validators/            # Zodバリデーション
├── middleware/            # Express Middleware
├── utils/                 # 汎用ユーティリティ
├── types/                 # 型定義
├── config/                # 定数
├── cron/                  # 定期実行バッジ処理
├── infra/                 # 外部システム連携
├── maintenance/           # 管理者実行機能
├── prototype/             # 未使用仮置きロジック
├── scripts/               # CLI実行スクリプト
├── bin/                   # www
├── errors.ts              # AppError等
├── db.ts                  # Sequelizeをdbにつなぐ
└── ...
```

## レイヤー構成

```
Frontend
    ↓
Route
    ↓
Controller
    ↓
UseCase
    ↓
Service
    ↓
Model
    ↓
Database
```

データは上から下へ流れることを基本とする。

## レイヤー依存

各レイヤーは直下のレイヤーのみを呼び出す。

例

Route → Controller → UseCase → Service → Model

Controller から Service を直接呼ばない。

UseCase から Model を直接呼ばない。

責務

Route
ルーティングのみ

Controller
HTTP 処理のみ

UseCase
業務ロジックのみ

Service
DB アクセスのみ

許可

Route
→ Controller

Controller
→ UseCase

UseCase
→ Service
→ Utils

Service
→ Model

Model
→ Sequelize

禁止

Route → Service
Route → Model

Controller → Model

UseCase → Express

Service → Express

## 基本方針

- 各レイヤーは責務を守る
- 他レイヤーの責務を持ち込まない
- 既存の設計方針に合わせる
- 詳細な実装ルールは各ディレクトリの AGENTS.md に従う
- 新しい実装を行う前に、同じ種類の既存実装を確認し、命名・構成・実装方法をできるだけ合わせる。既存の設計を壊す新しい書き方は行わない。

## ユーザー向け文章

ユーザーへ表示する文章（お知らせ、メール、通知、画面メッセージ、エラーメッセージなど）は、
使いやすいアプリがユーザーへ自然に話しかけるような文章を心掛ける。

文章は、親しみやすく、分かりやすく、安心感のあるものにする。

専門用語や開発者向けの表現はできるだけ避け、
初めて利用するユーザーでもすぐ理解できる文章を書く。

丁寧語（です・ます調）を基本とし、
必要以上に堅い敬語や事務的な表現は使用しない。

一文はできるだけ短くし、
読みやすさを優先する。

エラーが発生した場合は、
何が起きたのかだけではなく、
ユーザーが次に何をすればよいかも伝える。

ユーザーを責めるような表現や、
不安を与える表現は避ける。

「正常終了しました」「処理を実行しました」
「認証に失敗しました」のような機械的な文章ではなく、

「保存しました」
「もう一度お試しください」
「注文が完了しました」

のように、自然でシンプルな表現を優先する。

迷った場合は、

「初めて利用するユーザーでも、
説明なしで理解できるか」

を基準に文章を作成する。

## 単体テストの共通ルール

この節はserver/src配下の単体テストに適用する。単体テストは対象本番コードに最も近いtestディレクトリに置く。配置は [test/AGENTS.md](../test/AGENTS.md)、設計は [設計書規則](../test/docs/architecture/AGENTS.md)、結果は [レポート規則](../test/docs/report/AGENTS.md)、データ準備は [fixture規則](../test/fixtures/AGENTS.md) を参照する。

対象の実装と明示された契約から期待値を定め、観測・修正案・実装済み・検証済みを区別する。テストを通す目的で期待値を現行挙動へ合わせず、仕様の不一致は報告する。テスト追加だけを根拠に対象外の本番コード・設定・既存テストやライブラリを変更しない。

### テストコードと fixture のルール

- TypeScript・ESM で記述し、相対 import の拡張子は `.js` にする。型のみの import は `import type` を使う。
- テストは既存の Vitest、Router の HTTP 検証は Supertest を使用する。
- `describe` は責務・観点・優先度が分かる単位に分ける。テスト名はケース ID と日本語の条件・期待結果を含める。
- 同じ検証構造の入力違いは `it.each`、`describe.each` で展開し、失敗した値や項目をテスト名から特定できるようにする。
- 準備、対象の呼出し、結果の検証を読み取れる構成にする。共通化は fixture や反復する検証を中心とし、何を検証しているか隠す抽象化を避ける。
- 標準入力は実 schema を通過する値にする。個別ケースでは原則として検証対象の条件だけを変え、ほかの条件を正常に保つ。
- body、配列、入れ子のオブジェクト、既存データ相当の値は factory でテストごとに新しく作る。共有オブジェクトの変更を次のケースへ持ち越さない。
- 更新前後、複数ユーザー、複数画像などは区別できる値を使い、取り違えを検出できるようにする。不要なランダム値に依存しない。
- fixture 操作の helper で実装の変換・業務ロジックを再実装しない。期待値は検証する契約から明示する。
- `any` を避け、既存の型、`ReturnType`、`Parameters`、型付きモックを利用する。型アサーションは部分的な Request・Response や依存オブジェクト、意図的な型不正入力など必要な境界に限定する。
- 通常の HTTP 経路では到達しない入力で防御分岐を確認する場合は、テスト名・コメント・設計書でその前提を明示する。通常入力の保証と混同しない。
- コメントは責務の境界、意図的な型不正、制御が必要な理由などを説明する。デバッグ用ログを残さない。

### モックとテスト間の独立性

- モックには Vitest の `vi.hoisted`、`vi.mock`、`vi.fn`、`vi.spyOn` を使用する。モジュールモックから参照する関数群は必要に応じて `vi.hoisted` へまとめる。
- 検証対象の関数は実処理を呼び、依存先をモックする。対象そのものをモックして、設定した戻り値だけを検証しない。
- `beforeEach` でモック履歴・実装をリセットし、標準 fixture と正常系の応答を設定し直す。ケース固有の応答・例外は各テスト内で設定する。
- 時刻や識別子生成に依存する処理は既知の値で制御する。別呼出しを区別するケースでは、既知の異なる識別子を順に返す。
- spy、fake timer、環境変数の差替えは `afterEach` で復元する。必要に応じてタイマーを破棄し、モジュール内の状態は `vi.resetModules` と再 import で分離する。
- 外部サービスの通信・署名処理は境界でモックし、引数と返却値の利用を検証する。実際のアップロードや外部サービス内部の処理まで成功したとは記載しない。
- 認証に必要な鍵はテスト用に生成し、環境変数は `vi.stubEnv` で設定する。実環境の認証情報を読み込まないよう、必要に応じて dotenv をモックする。

### アサーションの共通ルール

- 正常系は戻り値に加え、依存先への引数、呼出し回数、必要な順序を確認する。主要な引渡しオブジェクトと公開レスポンスは、余分な項目も検出できる完全一致を基本とする。
- `toMatchObject` はケースの関心が一部項目に限られる場合に使う。同じオブジェクトを渡す契約は、値の一致だけでなく `toBe` による参照同一性も検証する。
- 書き換える項目だけでなく、更新引数やレスポンスへ含めてはいけない項目も確認する。
- `AppError` は型、`code`、`statusCode` を確認する。予期しない例外は元の Error オブジェクトがそのまま伝播することを検証する。
- 異常系は依存処理を一つずつ失敗させ、後続の検証・署名・更新などが呼ばれないことを確認する。早期 return では不要な検索・作成がないことも確認する。
- 複数の不備があるケースでエラーの優先順位を確認する。既に開始した並行処理の取消しなど、実装にない保証は期待しない。
- 配列・辞書は件数、順序、元 index・識別子と値の対応、欠落・重複を検証する。配列を詰めた後の位置と元 index を混同しない。
- 数値境界は下限・上限の直前／一致／直後を確認し、0、負数、小数、文字列、null、undefined、欠落を区別する。空文字・空配列、optional・nullable、入れ子の各階層も対象に応じて確認する。

### 非同期処理・重複実行・並行処理

- Promise を返す対象と非同期アサーションは必ず await する。開始した処理を未回収のままテストを終了しない。
- 待機や完了順の検証には `fixtures.ts` の deferred Promise の形式を用い、開始通知と解放用 Promise を分ける。任意の sleep や偶然の実行順に依存しない。
- 前段を保留している間に後続が実行されないこと、全処理の完了前に usecase が成功を返さないこと、解放後に期待する順序で進むことを確認する。
- 呼出し順の assert だけで await を保証したとしない。待機が契約となる箇所は、Promise を保留するテストを設ける。
- 並行処理は正順・逆順・混在、飛び飛びの index など、問題を再現できる手順を明示する。別呼出しの結果が混ざらないことも確認する。
- reject を操作する場合は先に拒否の検証を登録し、残った処理も解放・回収する。途中の assert が失敗しても後片付けが必要な場合は `try/finally` を用いる。
- 逐次 2 回の実行と並行実行を分ける。2 回目の検索結果を変えるモックでは、その前提を明記し、一般的な重複排除や一意性の保証へ拡大しない。

### 境界と確認方法

- 単体テストでは対象を実行し、DB・AWS等の外部依存は境界でモックする。モックは現在の実import先へ合わせ、同じcontrollerが読み込む対象外usecaseなどから実DB設定読込みへ進まないことも確認する。
- 実helperとの接続・HTTP・実DBの効果を確認する場合はintegrationへ分け、単体の成功だけでそれらの検証済みと扱わない。失敗を隠すskip・todo化やassert緩和はしない。
- server/で `npm run test:run -- src/<対象のtest>/`、`npm run lint`、`npm run typecheck`、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` を実行する。本番typecheckはtestを除外するため、単体テストの型はテスト用tsconfigで確認する。
- lint・型検査の対象を確認し、必要なら既存ESLintとtypescript-eslintで対象TSを追加検査する。共有設定を検査のためだけに変更しない。
- 既知エラー・環境制約・未実行と今回起因の失敗を区別し、ケースID・件数・モック範囲・残る確認をレポートに残す。対象外の問題はdocs/todoに記録する。最後に差分と変更範囲を確認する。

### utils配下の単体テスト

utils配下には現在これより近いAGENTS.mdがないため、本節を適用する。utilityは実処理を実行し、AWS SDK・ファイルI/O・子プロセス等は対象の責務に応じた境界で制御する。署名utilityは依存先への引数・制約・戻り値の同一参照・失敗時の後続停止を確認し、AWS通信やアップロードの成功とは扱わない。timer・イベントlistener・一時ファイル等を作る場合は終了時に復元・解除・後片付けを行う。
