# テスト設計書の共通ルール

## 適用範囲と配置

`server/test/docs/architecture` 配下の設計書に適用する。上位のAGENTS.mdと [配置規則](../../AGENTS.md) に従い、`<大分類>/<小分類>.md` に置く。例は [itemEditing/updateConfirm.md](itemEditing/updateConfirm.md)。過去の観測と最新の修正後契約を区別し、項目・数値・エラーコード・ケース数を他機能へ一律適用しない。

対象の本番コードと単体・結合テスト、fixture、[レポート](../report/AGENTS.md) を調査し、現配置を記載する。設計だけの依頼では実装・テスト・設定を変更しない。

## 作業範囲と期待結果の根拠

- テスト対象の usecase と、関係する helper、service、validator、middleware、controller、route、型を調査し、処理順序と責務の境界を把握する。
- 期待結果は対象の実装と明示された仕様・変更指示を根拠に定める。実装にない入力制約、状態遷移、重複排除などを推測で追加しない。
- 現行挙動の確認、提案する修正後の契約、実装済み・検証済みの結果を区別する。望ましい仕様が確定していない挙動は「観測」と明記する。
- 指定された契約と実装が一致しない場合は、不一致を報告する。テストを通す目的で期待値を現行実装へ合わせない。変更指示によって契約が更新された場合は、その根拠を記録して設計・期待値を更新する。
- 設計のみの依頼では設計書だけを作成・変更する。テスト作成の依頼を、実装コードや無関係な既存テストの修正許可と解釈しない。
- 対象外の不具合、改善点、既知のエラーは勝手に修正せず、`/docs/todo/AGENTS.md` の運用に従って記録する。
- 新しいライブラリや共通基盤を独断で追加しない。テストのためだけの分岐・待機処理を実装コードへ追加しない。

## 設計書のルール

テスト実装に先立ち、`<小分類>.md` に以下を整理する。既に設計書がある場合は内容と変更履歴を確認し、依頼範囲内で不足を補う。

1. 対象 usecase・関数、目的、作業範囲、対象外。
2. 調査した関連ファイルと各責務。パスの基準ディレクトリを明示する。
3. 処理の流れ、入力検証・業務判断・応答の境界、異常時に停止する位置。
4. テストのレベル、実処理にする範囲、モックする依存、確認できる範囲。
5. 標準 fixture、ケース別の変更点、共通アサーション。
6. ケース一覧、実装優先度、実行方法、完了条件。

ケース表には「ケース ID・レベル・条件／入力／手順・期待結果」を記載する。異常系にはエラーだけでなく後続の未実行処理も書く。主要な引渡し項目が多い場合は、入力・変換元と引渡し先の対応表を設ける。

正常系、異常系、境界値、条件分岐、状態の変化、重複実行、並行処理、controller・Router への接続を検討する。該当しない観点は理由を示し、対象にない保証を追加しない。

- ケース ID は `N01`、`E01`、`V01`、`R01` など、観点と連番が分かる形式にする。helper 固有の観点は対象に応じて命名する。
- 観測ケースは `O01` などで通常の期待仕様と区別する。
- 同じ ID の複数条件は表で明確にし、実装時に独立したテストへ展開する。
- 優先度は P0（基本動作・重要な入力境界・異常時停止）→ P1（helper の分岐・各層の接続）→ P2（重複実行・順序を制御した並行処理・観測）を基本とする。

DB を使う場合は、接続環境、必要なテーブル・制約、fixture の作成・削除範囲、transaction の境界も設計書に記載する。各ケースが「モックで呼出し契約を確認するもの」か「実 DB の保存結果を確認するもの」かを区別する。過去の未実施項目を追加する場合は、元のケース ID と残っている検証内容を対応付ける。

## 配置・責務・モックの記載

- 単体テストは対象本番コードに最も近いsrc配下のtest、結合テストはintegration/役割/大分類/小分類、fixtureはfixtures/大分類/小分類へ分け、ファイルごとの役割と検証範囲を示す。
- usecase単体、実helperとの接続、モデルメソッドをモックするservice単体、HTTP接続、実DBの保存結果を区別する。helperをモックするusecase単体だけでhelper分岐を検証済みにしない。
- 標準factory・deferred・DB setup・DB fixtureの責務を分け、空ファイルや件数合わせのケースを作らない。同じassertを全レイヤーへ機械的に複製しない。
- 単体コードのルールはserver/srcの最も近いAGENTS.md、結合テストは [database](../../integration/database/AGENTS.md)・[usecases](../../integration/usecases/AGENTS.md)、データ準備は [fixtures](../../fixtures/AGENTS.md) を参照する。

## 修正案と追加テスト設計

- 修正ID（F1等）、対象ファイル、原因、修正前の再現条件、修正後の契約、対象外を明示する。レポートの観測結果と元ケースIDを根拠とし、未確認事項から修正が必要と断定しない。
- 追加ケースはAF-<観点><連番>とし、元ケースID・レベル・入力/手順・修正後期待値の対応表を作る。正常・異常・境界・後続未実行・helper接続・必要な重複/並行処理を扱う。
- 既存ケースの維持・期待値更新・別責務への移行を区別する。契約が変わる箇所だけ更新し、無関係なassertを弱めない。旧不具合の観測を変更するのは修正実装後とし、旧結果は履歴として残す。
- 過去のDB未実施項目を補うときは現行コード・スキーマ・環境を再確認し、元IDと今回追加する確認範囲を対応付ける。単なる未実施補完と修正後の契約変更を区別する。
- 修正案・実行結果は同じ小分類の [統合レポート](../report/AGENTS.md) に記録し、設計との参照を結ぶ。afterFix.mdを別作成せず、実装前の提案と修正後の結果を混同しない。

## 記載の確認

パスの基準・リンク先・ケースID対応・優先度・完了条件と変更範囲を確認する。文書だけの変更ではテストを再実行していない旨を報告する。実行環境の制約・既知エラー・未確認を成功に混ぜず、対象外の改善はdocs/todoの運用に従う。
