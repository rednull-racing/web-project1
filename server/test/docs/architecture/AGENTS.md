# テスト設計書の共通ルール

## 適用範囲・配置・参考資料

`server/test/docs/architecture` 配下に適用する。上位の AGENTS.md と [配置規則](../../AGENTS.md) に従い、`<大分類>/<小分類>.md` に置く。usecase に限らず middleware・共通処理・DB 初期化も対象となる。

対応する [レポート](../report/AGENTS.md)、詳細設計、対象コード、既存テスト・fixture を調査する。パスは原則 `server/` 基準と明記し、リポジトリルート基準の参照は区別する。未作成のテストは「予定配置」とし、現配置や実装済みと混同しない。

参考例は目的別に選ぶ。大きな文書の章数・ケース数・固有仕様をそのまま複製しない。

- [createItem](items/createItem.md)：保存項目、在庫変換、通知、複数テーブルの整合性。
- [deleteItemDraft](itemDraft/deleteItemDraft.md)：停止位置、所有権、削除・編集開始の競合。
- [ErrorHandler](ErrorHandler/errorHandler.md)：共通 middleware、公開情報、実 parser との接続。
- [initialization](database/initialization.md)：短い設計、モジュール再読込み、環境変数・初期化の境界。

## 仕様の根拠と更新

- 設計日・調査時点、対象関数、目的、今回の成果物、対象外を記載する。設計のみの依頼ではテスト・本番コード・設定・DB を変更しない。
- 期待結果は明示された仕様・変更指示と対象コードを照合して定める。不一致は明記し、テストを通すために期待値を実装へ合わせない。未確定の挙動は「観測」として分ける。
- 過去の「未実装」「DB なし」や旧カラム・旧 import 先を現状とみなさず、現在のコードと配置を調べ直す。DB を直接確認していない場合は反映済みスキーマと断定しない。
- 契約や配置を変更した場合は日付・理由・元ケースとの対応を記載する。旧記述を残す場合は冒頭で優先する契約と履歴の範囲を示し、対応レポートへリンクする。
- 機能固有の ID 上限、必須項目、レート枠、重複防止、エラー形式を他機能へ一律適用しない。テスト作成の依頼を本番修正や共通基盤変更の許可と解釈しない。テスト用の分岐・待機処理を本番コードへ追加しない。

## 記載する内容

規模に応じて章をまとめてよい。短い設計ではケースの箇条書きも可とし、次の情報を追跡できるようにする。

1. 対象・目的・仕様の根拠・作業範囲・対象外。
2. 関連ファイルと責務、処理順序、入力・業務判断・保存・応答の境界。
3. テストレベル、ファイル配置、実処理・モック・障害注入の範囲と保証の限界。
4. 標準 fixture、ケース別の変更点、共通アサーション。コピーや変換が多い場合は取得元と保存先の対応表。
5. ケース ID・レベル、条件・入力・手順、期待結果、異常時の停止位置と後続未実行。
6. 実装優先度、実行ディレクトリと対象コマンド、完了条件、未確認事項。

詳細設計にテスト観点がある場合は各観点とケース ID を対応付ける。「ケースを設計した」ことと「実装・実行して成功した」ことを区別する。

## 敵対的なケースの検討

正常系の入力を少し変えるだけで終えず、**呼出し側が制約を破ろうとする場合や、依存先・実行順序が不利に働く場合を想定してケースを考える**。対象の責務に応じて、少なくとも次の観点を検討する。

- 所有権・認証：他人の ID、不存在・削除済み ID、所有者 null、body/query によるユーザー ID 偽装、無効・期限切れトークン。拒否時に他人の情報や内部情報が漏れないか。
- 入力：欠落・null・空値・不正型、上下限の直前／一致／直後、巨大整数・小数、数値へ変換される特殊表記、未知キー。任意値を一つ正常にして別の不正値が見逃されないか。
- 保存済みデータ：壊れた JSONB 構造、深い階層や後方要素の不正、関連欠落、必須値・FK の不整合。通常 fixture だけで破損経路を見落とさないか。
- 途中失敗・待機：依存処理を個別に reject／保留し、後続処理・成功応答が早まらないか。INSERT・DELETE 後の失敗、transaction 完了前後、通知失敗の影響を分ける。
- 再送・競合：同一対象の二重要求、失敗後の再試行、先行処理の commit／rollback、取得待機中の更新・削除・所有者変更。古い取得値で処理しないか、非対象行へ影響しないか。
- HTTP の組合せ：不正 JSON＋未認証、制限超過＋不正 body など複数の拒否条件でどこが先に止まるか。枠の消費、usecase・transaction・外部通信の未実行も確認する。

敵対的な入力を理由に新しい業務制約を発明しない。期待する拒否・停止・不変条件は確定仕様に基づけ、仕様未確定なら観測ケースにする。HTTP JSON では表現できない undefined・NaN・Infinity・疎配列等の直接注入は、HTTP や JSONB 経由の検証と分ける。対象にない観点は理由を短く記載し、無関係なケースを増やさない。

## ケース ID・優先度・検証境界

- ID は `N01`、`E01`、`V01` 等の観点と連番が分かる形式を使い、既存 ID を維持する。接頭辞とレベル記号は文書内で説明し、全機能で同じ意味と仮定しない。観測は `O01` 等で区別する。
- 同じ ID の複数条件を列挙し、実装時に独立したテストへ展開する。設計 ID 数、表の行数、`it.each` 展開後の件数を混同しない。
- 優先度は P0（基本契約・入力境界・所有権・原子性）、P1（helper 分岐・層間接続）、P2（重複・並行・観測）を目安とし、重要な競合は対象に応じて優先する。ケース ID の `P01` と優先度 `P0` は別物とする。
- usecase 単体、実 helper 接続、Model メソッドをモックする service 単体、HTTP、実 DB を区別する。配置ディレクトリ名だけで DB 接続の有無を判断しない。
- 認証・schema・errorHandler の実接続と usecase 直接呼出しの契約を分ける。HTTP の後続未実行には到達可能な正常対照を設け、最小 Express と実アプリ登録全体の検証範囲を区別する。
- Router・controller の import が対象外の usecase や DB 初期化を読み込む可能性も調べる。DB 非接続テストは現在の import 先で依存を遮断し、env の追加で隠さない。
- await は deferred 等で依存処理・transaction 外側の完了を別々に保留して設計する。commit 後の通知開始と通知完了待ちも対象の契約に応じて分ける。
- 単体は対象コードに最も近い `src/**/test`、結合は [database](../../integration/database/AGENTS.md)・[usecases](../../integration/usecases/AGENTS.md)、準備処理は [fixtures](../../fixtures/AGENTS.md) に従う。同じ assert を全レベルへ機械的に複製しない。

## 実 DB・transaction・並行処理がある場合

- `server/.env.test` 由来の PostgreSQL `test_db` を前提に、DB import 前の設定検査と接続後の実 DB 名検査を設計する。アプリ用・models 用・observer・競合用の全接続を対象とし、確認前に fixture を書き込まない。認証情報・接続 URL 全体を記載しない。
- 必要テーブル・型・NULL・FK・unique 等と反映済みスキーマを照合する範囲を示す。Model validation と実 DB 制約は別に検証し、不足をテストから migration や sync で自動補正しない。
- commit 前後の別接続可視性、rollback 後の新規 SELECT、全コピー値・関連行・非対象行の不変、再試行とロック解放を対象に応じて設計する。モックの transaction 成功を実 DB の原子性とみなさない。
- 独立 transaction・接続で先行の実ロック取得→後続開始→実待機→解放→完了を制御する。`pg_blocking_pids` 等で対象 PID の待機を確認し、固定 sleep や `Promise.all` だけを排他の根拠にしない。分離レベル・接続プール・上限時間・失敗時の全 gate 解放と処理回収を記載する。
- fixture・本処理・競合処理の作成 ID を追跡し、処理回収後に自作 ID だけを FK 順で削除する。残存確認、hook/spy/env 復元、全接続 close まで含める。全件削除・TRUNCATE・sequence 巻戻しを前提にしない。
- callback 内障害、transaction Promise の模擬 reject、実 DB 制約エラー、実 COMMIT 応答喪失、HTTP 送信失敗を分ける。通信断で成否不明になるケースを「必ず rollback」と保証しない。

## 修正案・追加設計・確認

- 修正案と実行結果の本体は同じ小分類の [統合レポート](../report/AGENTS.md) にまとめる。設計書には現行契約と追加ケースを反映し、実行履歴を重複転記しない。`afterFix.md` は別作成しない。
- 修正 ID（`F1` 等）と元ケースを対応付け、追加ケースは `AF-ID01`、`AF-DB01` 等、既存文書に合う ID を付ける。単なる未実施部分の補完と契約変更を区別し、全追加ケースへ機械的に新 ID を振り直さない。
- 既存ケースの維持・期待値変更・責務移行を示す。旧挙動の観測は修正実装後に新契約へ移し、根拠と旧結果をレポートに残す。無関係な assert を弱めない。
- 対象 Vitest、`npm run lint`、`npm run typecheck`、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` の計画を記載する。本番型検査とテスト型検査の対象差、通常 lint 対象外 TS の追加検査を確認し、共有設定を独断変更しない。
- 最後に相対リンク・パス・ケース対応・契約の優先関係・完了条件・差分を確認する。文書だけの変更ではテスト未実行と報告する。対象外の問題は `/docs/todo/AGENTS.md` に従い、編集範囲が明示的に限定される場合は許可された文書または最終回答へ残す。
