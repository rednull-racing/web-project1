# テストレポートの共通ルール

## 適用範囲と配置

`server/test/docs/report` 配下に適用する。上位のAGENTS.mdと [配置規則](../../AGENTS.md) に従い、`<大分類>/<小分類>.md` に初回報告・改善案・修正・再修正・再検証の記録をまとめる。afterFix.mdは別に作成しない。

[設計書規則](../architecture/AGENTS.md) と対象の設計書・コード・実行結果を照合する。基準例は [updateConfirmの統合レポート](itemEditing/updateConfirm.md)。最新結果を先に示し、過去の報告は実行日を付けた履歴として残す。修正案と実装済み・検証済みを明確に区別する。

## 報告書のルール

`<小分類>.md` は結果を先に示し、次の内容を記録する。

- 実行日、対象範囲、変更したファイル、完了した範囲。
- ファイル別と全体の実行件数、成功・失敗・skip・todo の件数。
- 実行ディレクトリ、再現できるコマンド、各確認の成否。
- 実処理とモックの範囲、テストで確認できること・確認していないこと。
- 設計ケース ID ごとの判定、対応テストファイル、確認内容、残る範囲。
- 観測した挙動の入力・再現手順・実際の結果。特に並行処理は開始・完了の順序を記録する。
- 未実装・未実行・対象外・環境制約とその理由、および既知のエラーと今回の変更に起因するエラーの区別。

設計項目数と `it.each` 展開後の実行件数は別々に集計する。複数 ID を一つのテストで確認する場合も対応が追えるようにする。件数は実際のランナー出力・JSON レポートから集計し、推測や過去の実行結果を今回の結果として記載しない。

「成功」「失敗」「一部実施」「対象外」「未実行」を区別する。観測テストの成功は、望ましい仕様であることや不具合の解消を意味しない。未作成・未実行のケースを skip 件数や成功件数へ混ぜない。

カバレッジを取得した場合は対象と行・分岐の結果、未実行部分の理由を報告する。高い割合やテスト件数だけを完了の根拠にせず、無関係な機能や不自然な fixture を増やして 100%を目指さない。

### DB テストで追加する報告

- 読み込んだ env ファイルのパス、設定上と実接続先の DB 名、ガードの確認結果を記載する。認証情報や接続 URL 全体は記載しない。
- DB テストと DB 非接続の回帰テストを分けて集計する。元の未実施・一部実施ケースごとに、今回確認した範囲と残る範囲を示す。
- 実 DB を使った処理、外部通信のモック、失敗を起こすために置換した処理、直接 SQL による検証を区別する。モデル validation と DB 制約、模擬した保存失敗と実 commit 障害を混同しない。
- commit・rollback 後の再取得方法、関連行の残存・重複、並行処理の取得・解放・完了順、非対象行への影響、後片付けの結果を記録する。
- 接続ガードによる中断、接続拒否、スキーマ不足、fixture 不備、実装と契約の不一致を分けて記録する。setup 失敗でランナーが skip と表示した場合も、ケース本体が実行されていないことを明記し、途中経過と最終集計を区別する。
- DB で観測した問題を修正していない場合は、その旨を書く。編集範囲の指定で docs/todo へ記録できない場合は、許可された報告書または最終回答へ残し、範囲外ファイルを編集しない。

## 修正案・追加テスト・再報告

- 修正案と追加テスト設計は同じ小分類の統合レポートにまとめ、初回報告の観測事項・元のケース ID を根拠として結び付ける。未確認の事項から修正の必要性を断定しない。
- 修正 ID（`F1` 等）、対象ファイル、原因、修正方針、修正後の契約、対象外を明示する。設計だけの段階では実装・検証済みと書かない。
- 追加ケースには `AF-<観点><連番>` の ID を付け、元のケース ID、レベル、入力・手順、修正後の期待結果を対応表にする。
- 修正前の再現条件と修正後の期待結果を対にし、正常系、異常系、境界、後続未実行、実 helper との接続、必要な重複・並行実行を確認する。
- 既存ケースを「維持」「期待値の変更」「別の責務のテストへ移行」などに整理する。仕様が変わる箇所だけ更新し、無関係な assert を弱めない。
- 不具合の旧挙動を期待する観測テストは、修正が実装された段階で新しい契約へ移行する。旧結果は過去の報告として残す。
- 失敗を隠すための削除、skip、todo 化をしない。元の件数を維持すること自体を目的にしない。
- 追加・移行後は対象ディレクトリの回帰テストを実行し、同じ小分類の統合レポートに修正レポートを追記する。変更内容、ケース対応、結果、未達事項、完了範囲を示す。
- 再修正では理由と契約の変更根拠を明記し、現行設計を更新したうえで再実行結果を追記する。以前の報告は実行履歴として残し、どの判定が最新か明確にする。

### DB 未実施項目の追加と修正後の確認

- DB が利用可能になったら、過去の報告書の未実施項目を洗い出し、依頼された範囲を実装する。過去の「専用 DB なし」「transaction 引数なし」などを現状とみなさず、現在のコード・スキーマ・接続環境を調査する。
- 元ケース ID を維持し、追加ケースには `AF-DB01` などの ID を付けて対応を記載する。DB 未実施部分の補完と、不具合修正後の契約変更を区別し、設計書と同じ小分類の統合レポートに根拠を残す。
- 共通 helper の移動や transaction 引数の追加などがあれば、実 import 先、モック先、引数の期待値を確認する。修正は依頼された範囲内で行い、実 DB へ意図せず接続する古いモックを残さない。
- 不一致は、fixture・テストの誤り、モデルと実 DB の差、アプリ実装の不具合に分けて調べる。期待値だけを変更して失敗を隠さず、観測結果を更新する場合も入力・実 SQL・最終行などの根拠を示す。
- rollback や重複防止の修正後は、戻り値や呼出し順だけでなく、関連行を含む実 DB 結果を再検証する。必要な正常系・異常系・再試行・並行ケースと、同じ対象ディレクトリの既存回帰を実行する。

## 検査・未達事項・変更範囲

- server/での対象Vitestコマンド、lint、本番typecheck、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` の対象と成否を記録する。本番typecheckはsrcのtestを除外し、テスト用tsconfigが単体・結合テストを含むことを区別する。
- 現行lint対象外のtest配下TSには既存ESLintとtypescript-eslintを使った追加lintの方法と結果を記録する。検査を通すために共有設定を変更しない。
- 対象内にエラーが報告されなかったことと検査全体の成功を区別し、失敗コマンド・原因・今回の変更との関係を示す。未実行のテストやDB処理は理由とともに明記する。
- 再実行や追加検証の結果を過去の件数へ重複加算しない。suite収集・setupの失敗、ケース本体の失敗、skip・todo・未処理例外を区別する。
- 観測した対象外の問題はdocs/todoへ記録し、許可された範囲外を修正しない。依頼範囲の重要な引数・結果・異常時停止・非同期待機・回帰が確認できた範囲だけを完了とする。
- 文書だけの変更では記載・リンク・ケース対応・差分を確認し、テストを再実行していない旨を明記する。
