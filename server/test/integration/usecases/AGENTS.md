# usecase・HTTP結合テストの共通ルール

## 適用範囲と配置

`server/test/integration/usecases` 配下に適用する。上位のAGENTS.mdと [配置規則](../../AGENTS.md) を読み、`<大分類>/<小分類>/` に配置する。実usecaseと複数helperの接続、transaction・並行処理、Routerから認証・validator・controller等への接続を扱う。

[設計書](../../docs/architecture/AGENTS.md)、[レポート](../../docs/report/AGENTS.md)、[fixture](../../fixtures/AGENTS.md) の該当ルールも読む。実DBを使う場合は必ず [DB結合テストの接続・安全・後片付け規則](../database/AGENTS.md) も適用する。

基準例は [updateConfirmの設計書](../../docs/architecture/itemEditing/updateConfirm.md) と [結合テスト](itemEditing/updateConfirm/)。過去の観測と最新の修正後契約を区別し、機能固有の項目・数値・ケース数は他機能へ一律適用しない。

## 作業範囲と期待結果の根拠

- テスト対象の usecase と、関係する helper、service、validator、middleware、controller、route、型を調査し、処理順序と責務の境界を把握する。
- 期待結果は対象の実装と明示された仕様・変更指示を根拠に定める。実装にない入力制約、状態遷移、重複排除などを推測で追加しない。
- 現行挙動の確認、提案する修正後の契約、実装済み・検証済みの結果を区別する。望ましい仕様が確定していない挙動は「観測」と明記する。
- 指定された契約と実装が一致しない場合は、不一致を報告する。テストを通す目的で期待値を現行実装へ合わせない。変更指示によって契約が更新された場合は、その根拠を記録して設計・期待値を更新する。
- 設計のみの依頼では設計書だけを作成・変更する。テスト作成の依頼を、実装コードや無関係な既存テストの修正許可と解釈しない。
- 対象外の不具合、改善点、既知のエラーは勝手に修正せず、`/docs/todo/AGENTS.md` の運用に従って記録する。
- 新しいライブラリや共通基盤を独断で追加しない。テストのためだけの分岐・待機処理を実装コードへ追加しない。

## テストコードと fixture のルール

- TypeScript・ESM で記述し、相対 import の拡張子は `.js` にする。型のみの import は `import type` を使う。
- テストは既存の Vitest、Router の HTTP 検証は Supertest を使用する。
- `describe` は責務・観点・優先度が分かる単位に分ける。テスト名はケース ID と日本語の条件・期待結果を含める。
- 同じ検証構造の入力違いは `it.each`、`describe.each` で展開し、失敗した値や項目をテスト名から特定できるようにする。
- 準備、対象の呼出し、結果の検証を読み取れる構成にする。共通化は fixture や反復する検証を中心とし、何を検証しているか隠す抽象化を避ける。
- 標準入力は実 schema を通過する値にする。個別ケースでは原則として検証対象の条件だけを変え、ほかの条件を正常に保つ。
- body、配列、入れ子のオブジェクト、既存データ相当の値は factory でテストごとに新しく作る。共有オブジェクトの変更を次のケースへ持ち越さない。
- 更新前後、複数ユーザー、複数画像などは区別できる値を使い、取り違えを検出できるようにする。不要なランダム値に依存しない。
- fixture 操作の helper で実装の変換・業務ロジックを再実装しない。期待値は検証する契約から明示する。
- `any` を避け、既存の型、`ReturnType`、`Parameters`、型付きモックを利用する。型アサーションは部分的な Request・Response や依存オブジェクト、意図的な型不正入力など必要な境界に限定する。
- 通常の HTTP 経路では到達しない入力で防御分岐を確認する場合は、テスト名・コメント・設計書でその前提を明示する。通常入力の保証と混同しない。
- コメントは責務の境界、意図的な型不正、制御が必要な理由などを説明する。デバッグ用ログを残さない。

## モックとテスト間の独立性

- モックには Vitest の `vi.hoisted`、`vi.mock`、`vi.fn`、`vi.spyOn` を使用する。モジュールモックから参照する関数群は必要に応じて `vi.hoisted` へまとめる。
- 検証対象の関数は実処理を呼び、依存先をモックする。対象そのものをモックして、設定した戻り値だけを検証しない。
- `beforeEach` でモック履歴・実装をリセットし、標準 fixture と正常系の応答を設定し直す。ケース固有の応答・例外は各テスト内で設定する。
- 時刻や識別子生成に依存する処理は既知の値で制御する。別呼出しを区別するケースでは、既知の異なる識別子を順に返す。
- spy、fake timer、環境変数の差替えは `afterEach` で復元する。必要に応じてタイマーを破棄し、モジュール内の状態は `vi.resetModules` と再 import で分離する。
- 外部サービスの通信・署名処理は境界でモックし、引数と返却値の利用を検証する。実際のアップロードや外部サービス内部の処理まで成功したとは記載しない。
- 認証に必要な鍵はテスト用に生成し、環境変数は `vi.stubEnv` で設定する。実環境の認証情報を読み込まないよう、必要に応じて dotenv をモックする。

## アサーションの共通ルール

- 正常系は戻り値に加え、依存先への引数、呼出し回数、必要な順序を確認する。主要な引渡しオブジェクトと公開レスポンスは、余分な項目も検出できる完全一致を基本とする。
- `toMatchObject` はケースの関心が一部項目に限られる場合に使う。同じオブジェクトを渡す契約は、値の一致だけでなく `toBe` による参照同一性も検証する。
- 書き換える項目だけでなく、更新引数やレスポンスへ含めてはいけない項目も確認する。
- `AppError` は型、`code`、`statusCode` を確認する。予期しない例外は元の Error オブジェクトがそのまま伝播することを検証する。
- 異常系は依存処理を一つずつ失敗させ、後続の検証・署名・更新などが呼ばれないことを確認する。早期 return では不要な検索・作成がないことも確認する。
- 複数の不備があるケースでエラーの優先順位を確認する。既に開始した並行処理の取消しなど、実装にない保証は期待しない。
- 配列・辞書は件数、順序、元 index・識別子と値の対応、欠落・重複を検証する。配列を詰めた後の位置と元 index を混同しない。
- 数値境界は下限・上限の直前／一致／直後を確認し、0、負数、小数、文字列、null、undefined、欠落を区別する。空文字・空配列、optional・nullable、入れ子の各階層も対象に応じて確認する。

## 非同期処理・重複実行・並行処理

- Promise を返す対象と非同期アサーションは必ず await する。開始した処理を未回収のままテストを終了しない。
- 待機や完了順の検証には `fixtures.ts` の deferred Promise の形式を用い、開始通知と解放用 Promise を分ける。任意の sleep や偶然の実行順に依存しない。
- 前段を保留している間に後続が実行されないこと、全処理の完了前に usecase が成功を返さないこと、解放後に期待する順序で進むことを確認する。
- 呼出し順の assert だけで await を保証したとしない。待機が契約となる箇所は、Promise を保留するテストを設ける。
- 並行処理は正順・逆順・混在、飛び飛びの index など、問題を再現できる手順を明示する。別呼出しの結果が混ざらないことも確認する。
- reject を操作する場合は先に拒否の検証を登録し、残った処理も解放・回収する。途中の assert が失敗しても後片付けが必要な場合は `try/finally` を用いる。
- 逐次 2 回の実行と並行実行を分ける。2 回目の検索結果を変えるモックでは、その前提を明記し、一般的な重複排除や一意性の保証へ拡大しない。

## 各層の接続と検証範囲

- 実処理にする層・モックする境界を設計書で明示する。usecase単体でhelperをモックした成功だけではhelper内部の分岐を検証済みとしない。
- 実helperとusecaseを接続する場合は値の変換元・引渡し先・処理順序・失敗後の停止位置を確認する。同じassertを全レイヤーへ機械的に複製しない。
- モデル操作をモックした呼出し契約、実DB保存、HTTP応答、実アプリのRouter登録は、それぞれ実行した範囲に限定して判定する。

### Router

- 最小の Express アプリへ JSON parser と対象 Router を明示的に接続し、Supertest で呼び出す。usecase をモックし、認証・validator・レート制限は実処理を使う。
- 正常応答、未認証・不正・期限切れトークン、params／body 不正、複数不正時の優先順位、usecase の未実行を確認する。
- レート制限は許容回数と次の 1 回、ユーザー別の枠、時間窓経過後の再開、不正入力が回数に含まれるかを実装に合わせて確認する。
- 時間制御は Date や interval など必要な対象に限定し、HTTP I/O を妨げない。テストごとに制限状態を分離する。
- テスト専用の 4 引数エラー middleware を使う場合は、エラー観測用であることを明示する。この結果を実アプリの Router 登録や共通 errorHandler の検証済みという意味にしない。

### transaction・並行処理

- 実DBを使う場合、商品本体と関連行が同じtransactionに参加することを実引数とcommit/rollback後の新規SELECTの両方で確認する。別接続の可視性と非対象行も検証する。
- 独立transaction・接続で順序を制御し、取得・ロック待機・解放・commit/rollback・完了を要求ごとに対応付ける。任意のsleepや偶然の実行順に依存しない。
- 逐次再実行、失敗後の再試行、並行実行を分け、実装にない再認可・一意性・排他制御を保証しない。保留処理は失敗時もtry/finallyで解放・回収する。
- `.env.test`以外の読込み、test_db以外、不明な接続先を検出したらDB処理を中断してユーザー判断を待つ。設定差替え・ガード緩和で続行しない。

## 実行確認と報告

server/で対象ファイルまたは `test/integration/usecases/<大分類>/<小分類>/` を指定して `npm run test:run -- <対象>`、`npm run lint`、`npm run typecheck`、`./node_modules/.bin/tsc --noEmit -p test/tsconfig.json` を実行する。実DBのないRouterテストにDB設定を持ち込まず、対象外usecaseも現在の実import先でモックする。

実DBを含む場合は接続条件・全接続ガードを先に確認する。ファイル間の干渉を抑える必要がある場合は理由を記録して `--maxWorkers=1` を使う。test配下のTSは現行lint設定の対象外なので、既存のESLintとtypescript-eslintで対象TSを追加検査する。検査を通すために共有設定を変更しない。

結果は [レポート規則](../../docs/report/AGENTS.md) に従い、DB非接続と実DBの件数、ケースID、モック範囲、未確認事項を区別する。失敗を隠すためのskip・todo化や期待値変更をしない。最後に変更範囲・参照パス・差分を確認する。
