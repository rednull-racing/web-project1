# usecase テストの共通ルール

## 適用範囲と必読事項

このファイルは `/server/test/usecases` 配下のすべてのテスト、fixture、設計書、報告書の新規作成・追加・変更に適用する。Codex は作業開始前に本書と上位の `AGENTS.md`、作業対象までの階層にある `AGENTS.md` を必ず読み、依頼された作業範囲を確認すること。

共通ルールの基準は [itemEditing/updateConfirm](./itemEditing/updateConfirm/) 内の各ファイルとする。他の usecase テストディレクトリの慣習を根拠に、本書のルールを変更しない。

- 設計の形式は [testArchitecture.md](./itemEditing/updateConfirm/testArchitecture.md) を参照する。
- 初回の実装・検証報告は [testReport.md](./itemEditing/updateConfirm/testReport.md) を参照する。
- 修正案、追加テスト、既存テストの移行、修正・再修正報告は [afterFix.md](./itemEditing/updateConfirm/afterFix.md) を参照する。
- テストコードの分割、fixture、モック、検証方法は同ディレクトリの `*.test.ts` と `fixtures.ts` を参照する。
- DB 接続の安全確認は [databaseSetup.ts](./itemEditing/updateConfirm/databaseSetup.ts)、データ作成・後片付け・別接続での確認は [databaseFixtures.ts](./itemEditing/updateConfirm/databaseFixtures.ts) を参照する。DB 検証の分け方は同ディレクトリの `database*.test.ts` を参照する。

参照元には初回の観測結果と修正後の契約が併存する。過去の報告を最新仕様と混同せず、変更の根拠と最新の修正・再修正報告を確認する。商品固有の項目名、数値、エラーコード、ケース数、ファイル数は他の usecase へ一律に適用しない。

## 作業範囲と期待結果の根拠

- テスト対象の usecase と、関係する helper、service、validator、middleware、controller、route、型を調査し、処理順序と責務の境界を把握する。
- 期待結果は対象の実装と明示された仕様・変更指示を根拠に定める。実装にない入力制約、状態遷移、重複排除などを推測で追加しない。
- 現行挙動の確認、提案する修正後の契約、実装済み・検証済みの結果を区別する。望ましい仕様が確定していない挙動は「観測」と明記する。
- 指定された契約と実装が一致しない場合は、不一致を報告する。テストを通す目的で期待値を現行実装へ合わせない。変更指示によって契約が更新された場合は、その根拠を記録して設計・期待値を更新する。
- 設計のみの依頼では設計書だけを作成・変更する。テスト作成の依頼を、実装コードや無関係な既存テストの修正許可と解釈しない。
- 対象外の不具合、改善点、既知のエラーは勝手に修正せず、`/docs/todo/AGENTS.md` の運用に従って記録する。
- 新しいライブラリや共通基盤を独断で追加しない。テストのためだけの分岐・待機処理を実装コードへ追加しない。

## ファイル構成と責務の分割

原則として `test/usecases/<機能>/<usecase名>/` に対象一式をまとめる。以下を基本構成とし、対象の責務に応じて必要なファイルを作成する。責務のない空ファイルや、参照元と件数を合わせるためのテストは作らない。

| ファイル                         | 役割                                                                                                      |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `testArchitecture.md`            | 初回テストの対象、根拠、責務、ケース、優先度、完了条件                                                    |
| `fixtures.ts`                    | 標準入力・既存データの factory、共通のエラー検証、deferred Promise                                        |
| `usecase.test.ts`                | 実 usecase と依存モックによる引数、戻り値、処理順序、失敗時の打切り                                       |
| `<対象helper名・関心事>.test.ts` | 実 helper の分岐、および必要な実 usecase との接続。参照元では `signedUrls.test.ts`、`masterBrand.test.ts` |
| `validation.test.ts`             | 実 schema、validateBody、validateParams の受理・拒否・値の引渡し                                          |
| `services.test.ts`               | 実 service から依存メソッドへの呼出し契約                                                                 |
| `controller.test.ts`             | 実 controller から usecase への引渡し、成功応答、例外の next への伝播                                     |
| `route.test.ts`                  | 実 Router・認証・validator・レート制限の接続                                                              |
| `databaseSetup.ts`               | `.env.test` の読込み、接続設定の検査、外部通信のモック。DB 関連モジュールの初期化より先に適用する         |
| `databaseFixtures.ts`            | 実 DB 名の検査、fixture の作成と後片付け、別接続での再取得、接続の終了                                    |
| `database.test.ts`               | 実 DB での永続化、制約、状態遷移、所有権、逐次再実行                                                      |
| `databaseTransactions.test.ts`   | commit・rollback、別接続からの可視性、関連行の整合性、失敗後の再試行                                      |
| `databaseConcurrency.test.ts`    | 実 DB 処理の順序を制御した並行更新、重複作成、所有者変更・削除との競合                                    |
| `testReport.md`                  | 初回の実装内容、実行結果、設計項目との対応、観測結果、未確認事項                                          |
| `afterFix.md`                    | 修正案、修正後のテスト設計、既存ケースの移行方針、修正・再修正報告                                        |

usecase 単体で helper をモックした場合、その成功だけで helper 内部の分岐を検証済みとしない。helper の実処理と usecase の組合せを必要な境界で確認し、同じ assert を全レイヤーへ機械的に複製しない。

## 設計書のルール

テスト実装に先立ち、`testArchitecture.md` に以下を整理する。既に設計書がある場合は内容と変更履歴を確認し、依頼範囲内で不足を補う。

1. 対象 usecase・関数、目的、作業範囲、対象外。
2. 調査した関連ファイルと各責務。パスの基準ディレクトリを明示する。
3. 処理の流れ、入力検証・業務判断・応答の境界、異常時に停止する位置。
4. テストのレベル、実処理にする範囲、モックする依存、確認できる範囲。
5. 標準 fixture、ケース別の変更点、共通アサーション。
6. ケース一覧、実装優先度、実行方法、完了条件。

ケース表には「ケース ID・レベル・条件／入力／手順・期待結果」を記載する。異常系にはエラーだけでなく後続の未実行処理も書く。主要な引渡し項目が多い場合は、入力・変換元と引渡し先の対応表を設ける。

正常系、異常系、境界値、条件分岐、状態の変化、重複実行、並行処理、controller・Router への接続を検討する。該当しない観点は理由を示し、対象にない保証を追加しない。

- ケース ID は `N01`、`E01`、`V01`、`R01` など、観点と連番が分かる形式にする。helper 固有の観点は対象に応じて命名する。
- 観測ケースは `O01` などで通常の期待仕様と区別する。
- 同じ ID の複数条件は表で明確にし、実装時に独立したテストへ展開する。
- 優先度は P0（基本動作・重要な入力境界・異常時停止）→ P1（helper の分岐・各層の接続）→ P2（重複実行・順序を制御した並行処理・観測）を基本とする。

DB を使う場合は、接続環境、必要なテーブル・制約、fixture の作成・削除範囲、transaction の境界も設計書に記載する。各ケースが「モックで呼出し契約を確認するもの」か「実 DB の保存結果を確認するもの」かを区別する。過去の未実施項目を追加する場合は、元のケース ID と残っている検証内容を対応付ける。

## テストコードと fixture のルール

- TypeScript・ESM で記述し、相対 import の拡張子は `.js` にする。型のみの import は `import type` を使う。
- テストは既存の Vitest、Router の HTTP 検証は Supertest を使用する。
- `describe` は責務・観点・優先度が分かる単位に分ける。テスト名はケース ID と日本語の条件・期待結果を含める。
- 同じ検証構造の入力違いは `it.each`、`describe.each` で展開し、失敗した値や項目をテスト名から特定できるようにする。
- 準備、対象の呼出し、結果の検証を読み取れる構成にする。共通化は fixture や反復する検証を中心とし、何を検証しているか隠す抽象化を避ける。
- 標準入力は実 schema を通過する値にする。個別ケースでは原則として検証対象の条件だけを変え、ほかの条件を正常に保つ。
- body、配列、入れ子のオブジェクト、既存データ相当の値は factory でテストごとに新しく作る。共有オブジェクトの変更を次のケースへ持ち越さない。
- 更新前後、複数ユーザー、複数画像などは区別できる値を使い、取り違えを検出できるようにする。不要なランダム値に依存しない。
- fixture 操作の helper で実装の変換・業務ロジックを再実装しない。期待値は検証する契約から明示する。
- `any` を避け、既存の型、`ReturnType`、`Parameters`、型付きモックを利用する。型アサーションは部分的な Request・Response や依存オブジェクト、意図的な型不正入力など必要な境界に限定する。
- 通常の HTTP 経路では到達しない入力で防御分岐を確認する場合は、テスト名・コメント・設計書でその前提を明示する。通常入力の保証と混同しない。
- コメントは責務の境界、意図的な型不正、制御が必要な理由などを説明する。デバッグ用ログを残さない。

## モックとテスト間の独立性

- モックには Vitest の `vi.hoisted`、`vi.mock`、`vi.fn`、`vi.spyOn` を使用する。モジュールモックから参照する関数群は必要に応じて `vi.hoisted` へまとめる。
- 検証対象の関数は実処理を呼び、依存先をモックする。対象そのものをモックして、設定した戻り値だけを検証しない。
- `beforeEach` でモック履歴・実装をリセットし、標準 fixture と正常系の応答を設定し直す。ケース固有の応答・例外は各テスト内で設定する。
- 時刻や識別子生成に依存する処理は既知の値で制御する。別呼出しを区別するケースでは、既知の異なる識別子を順に返す。
- spy、fake timer、環境変数の差替えは `afterEach` で復元する。必要に応じてタイマーを破棄し、モジュール内の状態は `vi.resetModules` と再 import で分離する。
- 外部サービスの通信・署名処理は境界でモックし、引数と返却値の利用を検証する。実際のアップロードや外部サービス内部の処理まで成功したとは記載しない。
- 認証に必要な鍵はテスト用に生成し、環境変数は `vi.stubEnv` で設定する。実環境の認証情報を読み込まないよう、必要に応じて dotenv をモックする。

## アサーションの共通ルール

- 正常系は戻り値に加え、依存先への引数、呼出し回数、必要な順序を確認する。主要な引渡しオブジェクトと公開レスポンスは、余分な項目も検出できる完全一致を基本とする。
- `toMatchObject` はケースの関心が一部項目に限られる場合に使う。同じオブジェクトを渡す契約は、値の一致だけでなく `toBe` による参照同一性も検証する。
- 書き換える項目だけでなく、更新引数やレスポンスへ含めてはいけない項目も確認する。
- `AppError` は型、`code`、`statusCode` を確認する。予期しない例外は元の Error オブジェクトがそのまま伝播することを検証する。
- 異常系は依存処理を一つずつ失敗させ、後続の検証・署名・更新などが呼ばれないことを確認する。早期 return では不要な検索・作成がないことも確認する。
- 複数の不備があるケースでエラーの優先順位を確認する。既に開始した並行処理の取消しなど、実装にない保証は期待しない。
- 配列・辞書は件数、順序、元 index・識別子と値の対応、欠落・重複を検証する。配列を詰めた後の位置と元 index を混同しない。
- 数値境界は下限・上限の直前／一致／直後を確認し、0、負数、小数、文字列、null、undefined、欠落を区別する。空文字・空配列、optional・nullable、入れ子の各階層も対象に応じて確認する。

## 非同期処理・重複実行・並行処理

- Promise を返す対象と非同期アサーションは必ず await する。開始した処理を未回収のままテストを終了しない。
- 待機や完了順の検証には `fixtures.ts` の deferred Promise の形式を用い、開始通知と解放用 Promise を分ける。任意の sleep や偶然の実行順に依存しない。
- 前段を保留している間に後続が実行されないこと、全処理の完了前に usecase が成功を返さないこと、解放後に期待する順序で進むことを確認する。
- 呼出し順の assert だけで await を保証したとしない。待機が契約となる箇所は、Promise を保留するテストを設ける。
- 並行処理は正順・逆順・混在、飛び飛びの index など、問題を再現できる手順を明示する。別呼出しの結果が混ざらないことも確認する。
- reject を操作する場合は先に拒否の検証を登録し、残った処理も解放・回収する。途中の assert が失敗しても後片付けが必要な場合は `try/finally` を用いる。
- 逐次 2 回の実行と並行実行を分ける。2 回目の検索結果を変えるモックでは、その前提を明記し、一般的な重複排除や一意性の保証へ拡大しない。

## DB 接続を使うテスト

### 実行環境と接続前の確認

DB テストは、`server/.env.test` を接続設定の読込元とし、PostgreSQL の `test_db` だけを使う。`NODE_ENV=test` を設定しただけでは、接続先の安全確認を済ませたことにはならない。

1. `server/` を実行ディレクトリとし、テストコマンド、dotenv の読込箇所、DB・モデルの import 経路を確認する。
2. DB 関連モジュールの初期化前に `.env.test` を読み、`NODE_ENV` が `test`、接続 URL の DB 名が `test_db` であることを検査する。シェルから引き継いだ接続設定をそのまま信用せず、実際に採用する設定が `.env.test` 由来であることを確認する。
3. アプリ用、モデル初期化用、結果確認用など、テストが使用するすべての接続について、接続前に Sequelize の設定 DB 名を検査する。
4. 接続後は `SELECT current_database()` で実 DB 名が `test_db` であることを確認する。この確認が終わるまで、fixture の作成や更新・削除を行わない。

- 検査はエージェントによる事前確認だけでなく、テストを再実行しても働くガードとして実装する。設定不足、URL 不正、DB 名不一致は、秘密情報を含まない明確なエラーで停止させる。
- モデルや config の引数なし `dotenv.config()` が `.env` を開く場合がある。参照実装のようにテスト内で読込みを制御し、検証済み `.env.test` の値だけを使う。dotenv をモックしたという事実だけで安全と判断しない。
- 接続設定を読込後に別の値で上書きしない。明示的な別 env ファイルの読込みや接続 URL の変更も検出する。DB を使わないテストには、import を通じた意図しない実 DB 接続を持ち込まない。
- 接続 URL 全体、ユーザー名・パスワード、トークン、env ファイルの内容をログや報告書へ出力しない。確認の証跡には、読込元のパス、DB 名、検査結果を記録する。

### 条件に違反したときの中断

**`.env.test` 以外の env ファイルをもとに接続している、または DB 名が `test_db` ではない場合は、テストの実行を中断し、続行の判断をユーザーに委ねる。** 読込元や接続先を確認できない場合も、推測で DB テストを開始・続行しない。

違反を検出したら後続の DB 処理を止め、確認できた事実、停止位置、書込みの有無を秘密情報なしで伝える。設定を黙って差し替えて再実行したり、ガードを外したりしない。接続先が不明な状態では、後片付けを理由に削除処理を流さない。書込みの有無が不明なら、その点も報告する。

この中断は、接続が拒否された場合とは区別する。サンドボックスによる通信拒否は実行環境の承認手順に従い、許可後も同じ接続ガードを通して再実行する。通信の許可を、別 DB の利用許可と解釈しない。安全条件を満たし、既に依頼で認められたテストの通常の再実行について、毎回確認を求める必要はない。

### スキーマとテストデータの準備・後片付け

- 既に用意されたテスト DB と反映済みスキーマを使用する。モデル、migration、実 DB の制約を確認し、不一致があれば報告する。テストを通すためにスキーマを自動補正しない。
- テスト実装・実行の依頼だけを根拠に、DB 作成、migration 実行、`sequelize.sync()`、テーブル全件削除、`truncate`を行わない。
- fixture は必要な親行・マスターを含めてテストごとに作成する。対象ユーザー、別ユーザー、更新対象行、影響してはいけない関連行を区別できる値にする。
- 他の実行と衝突しない固有名を使い、作成した ID を記録する。固定 ID や共有データの存在・不存在に依存する場合は、その前提を先に検査する。ランダム値は主にデータの分離へ使い、業務上の期待値は明示する。
- usecase が作成する関連行も後片付けの対象に含める。fixture 作成途中や assert の失敗時も、作成済みの行だけを外部キーの依存順に削除し、対象 ID の残存がないことを確認する。
- 削除条件を広げて既存データや他のテストの行を消さない。シーケンスの採番値は原則として戻さず、連続した ID を期待しない。
- 保留中の Promise と transaction を終了させてから後片付けを行う。追加した hook、SQL 記録、spy を解除し、すべての Sequelize 接続を閉じる。DB 接続のため suite 全体で保持する環境変数は、接続終了後の `afterAll` で復元してよい。

### テストコードで確認すること

DB テストでは、対象の usecase・helper・service・モデルと実 PostgreSQL を組み合わせる。外部サービスの通信は引き続き境界でモックする。障害注入や順序制御の spy を使う場合は、どこを置換し、どこまで実処理を実行したかを明示する。

| 観点            | 確認内容                                                                                                                                            |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 永続化          | 更新に使ったモデルインスタンスだけを見ず、新規 SELECT で保存値を取得する。主な保存項目、関連 ID、行数、配列の順序、JSONB の値・キーの有無を確認する |
| 非対象データ    | 他ユーザーの行、公開側などの関連行、所有者、作成日時など、変更してはいけない値が維持されることを確認する                                            |
| 所有権・状態    | where 条件の引数だけでなく、実際に対象外行が除外されること、エラー後に更新されないことを確認する                                                    |
| 制約            | 入力 schema、Sequelize の validation、DB の NOT NULL・ENUM・文字数・外部キー・unique 制約のどこで失敗したかを区別する                               |
| JSONB・nullable | `undefined`のキー省略、空配列、null、0、小数、日本語などを DB から再取得して確認する。モデル上の値だけで保存表現を断定しない                        |

モデル validation による拒否だけで、DB にも同じ制約があると報告しない。DB 制約自体を確認する必要がある場合は、テスト行を対象に直接 SQL などで検証し、通常の usecase 経路のテストと分ける。SQL の値にはバインドパラメータ等を使う。エラーは型・コード・発生箇所と、後続処理の未実行、DB への影響を確認する。

### transaction・再実行・並行処理

- transaction の callback 内で呼ばれているだけでは、関連行の書込みも同じ transaction へ参加しているとは限らない。usecase から helper・service・Model 操作までの引数を調べ、実 DB の commit・rollback 結果も確認する。
- 複数更新の途中で失敗させる場合は、先行更新が実際に完了したことを確認する。そのうえで別接続から再取得し、更新対象の全列と関連行が期待する状態に戻っているかを検証する。元のモデルインスタンスは rollback 後も変更済みの値を保持し得るため、判定に使わない。
- commit を確認するテストでは、必要な処理を保留して「commit 前は別接続から旧値、commit 後は新値」を確認する。テスト全体を外側の transaction で囲って常に rollback する方法だけでは、実 commit や別接続からの可視性を検証したことにならない。
- 同じ入力の逐次再実行、失敗後の再試行、並行実行を別ケースにする。関連行の件数・関連付け・再利用・部分更新の残存を確認し、逐次実行の成功から並行時の重複防止を推測しない。
- 並行テストは実 SELECT 後などの境界で開始通知と解放用 Promise を使い、「両方取得 →A commit→B commit」のように順序を固定する。同じ商品と別の商品、片方だけ rollback、参照先削除、所有者変更などを対象の責務に応じて検討する。
- 別接続での競合を扱う場合は、それぞれ独立した接続・transaction を使用する。待機中に別処理が失敗しても停止したままにならないようにし、`try/finally` 等で全処理を解放・回収する。
- 古いモデルインスタンスの変更検知により、更新される列や最終値が変わることがある。必要な SQL と最終行を併せて確認し、単純な「後勝ち」や、実装にない再認可・排他制御を保証しない。SQL 記録には秘密情報を含めず、確認後に hook を外す。

## 各層で確認すること

### validator・middleware

- 実 schema の `safeParse`／`parse` を使う。受理・拒否に加え、変換後の値、未知キーの除去、入力順の保持など対象の契約を確認する。
- validateBody／validateParams の成功時は検証済み値の格納と `next` の呼出しを確認する。失敗時はエラーと、正常系の `next` や検証済み値の設定が行われないことを確認する。
- 独自 refinement は拒否の有無だけでなく、エラーが付く項目・配列位置を確認する。
- schema で受理されることと、usecase の業務条件を満たすことを分ける。usecase や helper への直接呼出しで middleware の検証まで実行されると仮定しない。

### helper・service

- helper は優先順位、fallback、変換、戻り値、不要な後続呼出しの抑止を検証する。重要な結果は実 usecase へ接続し、次の処理へ正しく渡ることも確認する。
- URL 等を組み立てる helper は、既存値の再利用、新規生成条件、依存先へ渡すキーと返却 URL の対応を確認する。
- service 単体では依存メソッドをモックし、引数、回数、必要な順序、戻り値・参照の引渡しを確認する。モック先の実際の動作まで検証したとしない。DB テストでは実 service と実モデルを使い、取得・保存結果も確認する。

### controller

- usecase をモックし、実 controller を呼ぶ。認証済みユーザー、検証済み入力、ID の扱いを確認し、未検証 body に混入した別ユーザー ID 等を採用しないことを検証する。
- 成功時はステータスと返却項目を確認する。null、空配列、空辞書、値ありなどレスポンスの該当形を扱う。
- 失敗時は同じエラーを `next` へ渡し、成功レスポンスを送らないことを確認する。

### Router

- 最小の Express アプリへ JSON parser と対象 Router を明示的に接続し、Supertest で呼び出す。usecase をモックし、認証・validator・レート制限は実処理を使う。
- 正常応答、未認証・不正・期限切れトークン、params／body 不正、複数不正時の優先順位、usecase の未実行を確認する。
- レート制限は許容回数と次の 1 回、ユーザー別の枠、時間窓経過後の再開、不正入力が回数に含まれるかを実装に合わせて確認する。
- 時間制御は Date や interval など必要な対象に限定し、HTTP I/O を妨げない。テストごとに制限状態を分離する。
- テスト専用の 4 引数エラー middleware を使う場合は、エラー観測用であることを明示する。この結果を実アプリの Router 登録や共通 errorHandler の検証済みという意味にしない。

## 報告書のルール

`testReport.md` は結果を先に示し、次の内容を記録する。

- 実行日、対象範囲、変更したファイル、完了した範囲。
- ファイル別と全体の実行件数、成功・失敗・skip・todo の件数。
- 実行ディレクトリ、再現できるコマンド、各確認の成否。
- 実処理とモックの範囲、テストで確認できること・確認していないこと。
- 設計ケース ID ごとの判定、対応テストファイル、確認内容、残る範囲。
- 観測した挙動の入力・再現手順・実際の結果。特に並行処理は開始・完了の順序を記録する。
- 未実装・未実行・対象外・環境制約とその理由、および既知のエラーと今回の変更に起因するエラーの区別。

設計項目数と `it.each` 展開後の実行件数は別々に集計する。複数 ID を一つのテストで確認する場合も対応が追えるようにする。件数は実際のランナー出力・JSON レポートから集計し、推測や過去の実行結果を今回の結果として記載しない。

「成功」「失敗」「一部実施」「対象外」「未実行」を区別する。観測テストの成功は、望ましい仕様であることや不具合の解消を意味しない。未作成・未実行のケースを skip 件数や成功件数へ混ぜない。

カバレッジを取得した場合は対象と行・分岐の結果、未実行部分の理由を報告する。高い割合やテスト件数だけを完了の根拠にせず、無関係な機能や不自然な fixture を増やして 100%を目指さない。

### DB テストで追加する報告

- 読み込んだ env ファイルのパス、設定上と実接続先の DB 名、ガードの確認結果を記載する。認証情報や接続 URL 全体は記載しない。
- DB テストと DB 非接続の回帰テストを分けて集計する。元の未実施・一部実施ケースごとに、今回確認した範囲と残る範囲を示す。
- 実 DB を使った処理、外部通信のモック、失敗を起こすために置換した処理、直接 SQL による検証を区別する。モデル validation と DB 制約、模擬した保存失敗と実 commit 障害を混同しない。
- commit・rollback 後の再取得方法、関連行の残存・重複、並行処理の取得・解放・完了順、非対象行への影響、後片付けの結果を記録する。
- 接続ガードによる中断、接続拒否、スキーマ不足、fixture 不備、実装と契約の不一致を分けて記録する。setup 失敗でランナーが skip と表示した場合も、ケース本体が実行されていないことを明記し、途中経過と最終集計を区別する。
- DB で観測した問題を修正していない場合は、その旨を書く。編集範囲の指定で docs/todo へ記録できない場合は、許可された報告書または最終回答へ残し、範囲外ファイルを編集しない。

## 修正案・追加テスト・再報告

- 修正案と追加テスト設計は `afterFix.md` にまとめ、`testReport.md` の観測事項・元のケース ID を根拠として結び付ける。未確認の事項から修正の必要性を断定しない。
- 修正 ID（`F1` 等）、対象ファイル、原因、修正方針、修正後の契約、対象外を明示する。設計だけの段階では実装・検証済みと書かない。
- 追加ケースには `AF-<観点><連番>` の ID を付け、元のケース ID、レベル、入力・手順、修正後の期待結果を対応表にする。
- 修正前の再現条件と修正後の期待結果を対にし、正常系、異常系、境界、後続未実行、実 helper との接続、必要な重複・並行実行を確認する。
- 既存ケースを「維持」「期待値の変更」「別の責務のテストへ移行」などに整理する。仕様が変わる箇所だけ更新し、無関係な assert を弱めない。
- 不具合の旧挙動を期待する観測テストは、修正が実装された段階で新しい契約へ移行する。旧結果は過去の報告として残す。
- 失敗を隠すための削除、skip、todo 化をしない。元の件数を維持すること自体を目的にしない。
- 追加・移行後は対象ディレクトリの回帰テストを実行し、`afterFix.md` に修正レポートを追記する。変更内容、ケース対応、結果、未達事項、完了範囲を示す。
- 再修正では理由と契約の変更根拠を明記し、現行設計を更新したうえで再実行結果を追記する。以前の報告は実行履歴として残し、どの判定が最新か明確にする。

### DB 未実施項目の追加と修正後の確認

- DB が利用可能になったら、過去の報告書の未実施項目を洗い出し、依頼された範囲を実装する。過去の「専用 DB なし」「transaction 引数なし」などを現状とみなさず、現在のコード・スキーマ・接続環境を調査する。
- 元ケース ID を維持し、追加ケースには `AF-DB01` などの ID を付けて対応を記載する。DB 未実施部分の補完と、不具合修正後の契約変更を区別し、設計書と `afterFix.md` に根拠を残す。
- 共通 helper の移動や transaction 引数の追加などがあれば、実 import 先、モック先、引数の期待値を確認する。修正は依頼された範囲内で行い、実 DB へ意図せず接続する古いモックを残さない。
- 不一致は、fixture・テストの誤り、モデルと実 DB の差、アプリ実装の不具合に分けて調べる。期待値だけを変更して失敗を隠さず、観測結果を更新する場合も入力・実 SQL・最終行などの根拠を示す。
- rollback や重複防止の修正後は、戻り値や呼出し順だけでなく、関連行を含む実 DB 結果を再検証する。必要な正常系・異常系・再試行・並行ケースと、同じ対象ディレクトリの既存回帰を実行する。

## 実行確認と完了判定

テストコードを作成・変更した場合は、`server/` で次を実行する。`<対象ディレクトリ>` は今回の usecase のパスへ置き換える。

DB テストを含む場合は、先に本書の接続条件とガードを確認する。ファイル間の並列実行を抑える必要があれば `--maxWorkers=1` を指定し、その理由を記録する。この指定は、テスト内で明示的に制御する並行 DB 処理の代わりにはならない。

```bash
npm run test:run -- test/usecases/<対象ディレクトリ>/
npm run lint
npm run typecheck
./node_modules/.bin/tsc --noEmit -p test/tsconfig.json
```

- lint・型検査の実際の対象を確認する。テスト TS が lint 対象から外れている場合は、既存の ESLint と typescript-eslint を使って対象テストへの追加検査を行い、その方法と結果を記録する。検査を通すためだけに既存設定を変更しない。
- 既存エラーや実行環境の制限で失敗した場合は、コマンド、原因、今回の変更との関係を報告する。「変更ファイルのエラーが報告されなかった」と「検査全体が成功した」を区別する。
- 設計書・報告書だけを変更した場合は、記載・リンク・ケース対応・変更範囲を確認する。テストを再実行していない場合はその旨を明記する。
- 完了は、依頼範囲の必須ケース、異常時の後続未実行、重要な引数・戻り値、非同期処理の待機・順序、関連する回帰確認と報告の整合が確認できた範囲に限定する。
- 最後に差分を確認し、対象外のコード・テスト・設定の変更や、デバッグコードが混入していないことを確認する。
