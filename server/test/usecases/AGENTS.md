# usecaseテストの共通ルール

## 適用範囲と必読事項

このファイルは `/server/test/usecases` 配下のすべてのテスト、fixture、設計書、報告書の新規作成・追加・変更に適用する。Codexは作業開始前に本書と上位の `AGENTS.md`、作業対象までの階層にある `AGENTS.md` を必ず読み、依頼された作業範囲を確認すること。

共通ルールの基準は [itemEditing/updateConfirm](./itemEditing/updateConfirm/) 内の各ファイルとする。他のusecaseテストディレクトリの慣習を根拠に、本書のルールを変更しない。

- 設計の形式は [testArchitecture.md](./itemEditing/updateConfirm/testArchitecture.md) を参照する。
- 初回の実装・検証報告は [testReport.md](./itemEditing/updateConfirm/testReport.md) を参照する。
- 修正案、追加テスト、既存テストの移行、修正・再修正報告は [afterFix.md](./itemEditing/updateConfirm/afterFix.md) を参照する。
- テストコードの分割、fixture、モック、検証方法は同ディレクトリの `*.test.ts` と `fixtures.ts` を参照する。

参照元には初回の観測結果と修正後の契約が併存する。過去の報告を最新仕様と混同せず、変更の根拠と最新の修正・再修正報告を確認する。商品固有の項目名、数値、エラーコード、ケース数、ファイル数は他のusecaseへ一律に適用しない。

## 作業範囲と期待結果の根拠

- テスト対象のusecaseと、関係するhelper、service、validator、middleware、controller、route、型を調査し、処理順序と責務の境界を把握する。
- 期待結果は対象の実装と明示された仕様・変更指示を根拠に定める。実装にない入力制約、状態遷移、重複排除などを推測で追加しない。
- 現行挙動の確認、提案する修正後の契約、実装済み・検証済みの結果を区別する。望ましい仕様が確定していない挙動は「観測」と明記する。
- 指定された契約と実装が一致しない場合は、不一致を報告する。テストを通す目的で期待値を現行実装へ合わせない。変更指示によって契約が更新された場合は、その根拠を記録して設計・期待値を更新する。
- 設計のみの依頼では設計書だけを作成・変更する。テスト作成の依頼を、実装コードや無関係な既存テストの修正許可と解釈しない。
- 対象外の不具合、改善点、既知のエラーは勝手に修正せず、`/docs/todo/AGENTS.md` の運用に従って記録する。
- 新しいライブラリや共通基盤を独断で追加しない。テストのためだけの分岐・待機処理を実装コードへ追加しない。

## ファイル構成と責務の分割

原則として `test/usecases/<機能>/<usecase名>/` に対象一式をまとめる。以下を基本構成とし、対象の責務に応じて必要なファイルを作成する。責務のない空ファイルや、参照元と件数を合わせるためのテストは作らない。

| ファイル | 役割 |
| --- | --- |
| `testArchitecture.md` | 初回テストの対象、根拠、責務、ケース、優先度、完了条件 |
| `fixtures.ts` | 標準入力・既存データのfactory、共通のエラー検証、deferred Promise |
| `usecase.test.ts` | 実usecaseと依存モックによる引数、戻り値、処理順序、失敗時の打切り |
| `<対象helper名・関心事>.test.ts` | 実helperの分岐、および必要な実usecaseとの接続。参照元では `signedUrls.test.ts`、`masterBrand.test.ts` |
| `validation.test.ts` | 実schema、validateBody、validateParamsの受理・拒否・値の引渡し |
| `services.test.ts` | 実serviceから依存メソッドへの呼出し契約 |
| `controller.test.ts` | 実controllerからusecaseへの引渡し、成功応答、例外のnextへの伝播 |
| `route.test.ts` | 実Router・認証・validator・レート制限の接続 |
| `testReport.md` | 初回の実装内容、実行結果、設計項目との対応、観測結果、未確認事項 |
| `afterFix.md` | 修正案、修正後のテスト設計、既存ケースの移行方針、修正・再修正報告 |

usecase単体でhelperをモックした場合、その成功だけでhelper内部の分岐を検証済みとしない。helperの実処理とusecaseの組合せを必要な境界で確認し、同じassertを全レイヤーへ機械的に複製しない。

## 設計書のルール

テスト実装に先立ち、`testArchitecture.md` に以下を整理する。既に設計書がある場合は内容と変更履歴を確認し、依頼範囲内で不足を補う。

1. 対象usecase・関数、目的、作業範囲、対象外。
2. 調査した関連ファイルと各責務。パスの基準ディレクトリを明示する。
3. 処理の流れ、入力検証・業務判断・応答の境界、異常時に停止する位置。
4. テストのレベル、実処理にする範囲、モックする依存、確認できる範囲。
5. 標準fixture、ケース別の変更点、共通アサーション。
6. ケース一覧、実装優先度、実行方法、完了条件。

ケース表には「ケースID・レベル・条件／入力／手順・期待結果」を記載する。異常系にはエラーだけでなく後続の未実行処理も書く。主要な引渡し項目が多い場合は、入力・変換元と引渡し先の対応表を設ける。

正常系、異常系、境界値、条件分岐、状態の変化、重複実行、並行処理、controller・Routerへの接続を検討する。該当しない観点は理由を示し、対象にない保証を追加しない。

- ケースIDは `N01`、`E01`、`V01`、`R01` など、観点と連番が分かる形式にする。helper固有の観点は対象に応じて命名する。
- 観測ケースは `O01` などで通常の期待仕様と区別する。
- 同じIDの複数条件は表で明確にし、実装時に独立したテストへ展開する。
- 優先度はP0（基本動作・重要な入力境界・異常時停止）→ P1（helperの分岐・各層の接続）→ P2（重複実行・順序を制御した並行処理・観測）を基本とする。

## テストコードとfixtureのルール

- TypeScript・ESMで記述し、相対importの拡張子は `.js` にする。型のみのimportは `import type` を使う。
- テストは既存のVitest、RouterのHTTP検証はSupertestを使用する。
- `describe` は責務・観点・優先度が分かる単位に分ける。テスト名はケースIDと日本語の条件・期待結果を含める。
- 同じ検証構造の入力違いは `it.each`、`describe.each` で展開し、失敗した値や項目をテスト名から特定できるようにする。
- 準備、対象の呼出し、結果の検証を読み取れる構成にする。共通化はfixtureや反復する検証を中心とし、何を検証しているか隠す抽象化を避ける。
- 標準入力は実schemaを通過する値にする。個別ケースでは原則として検証対象の条件だけを変え、ほかの条件を正常に保つ。
- body、配列、入れ子のオブジェクト、既存データ相当の値はfactoryでテストごとに新しく作る。共有オブジェクトの変更を次のケースへ持ち越さない。
- 更新前後、複数ユーザー、複数画像などは区別できる値を使い、取り違えを検出できるようにする。不要なランダム値に依存しない。
- fixture操作のhelperで実装の変換・業務ロジックを再実装しない。期待値は検証する契約から明示する。
- `any` を避け、既存の型、`ReturnType`、`Parameters`、型付きモックを利用する。型アサーションは部分的なRequest・Responseや依存オブジェクト、意図的な型不正入力など必要な境界に限定する。
- 通常のHTTP経路では到達しない入力で防御分岐を確認する場合は、テスト名・コメント・設計書でその前提を明示する。通常入力の保証と混同しない。
- コメントは責務の境界、意図的な型不正、制御が必要な理由などを説明する。デバッグ用ログを残さない。

## モックとテスト間の独立性

- モックにはVitestの `vi.hoisted`、`vi.mock`、`vi.fn`、`vi.spyOn` を使用する。モジュールモックから参照する関数群は必要に応じて `vi.hoisted` へまとめる。
- 検証対象の関数は実処理を呼び、依存先をモックする。対象そのものをモックして、設定した戻り値だけを検証しない。
- `beforeEach` でモック履歴・実装をリセットし、標準fixtureと正常系の応答を設定し直す。ケース固有の応答・例外は各テスト内で設定する。
- 時刻や識別子生成に依存する処理は既知の値で制御する。別呼出しを区別するケースでは、既知の異なる識別子を順に返す。
- spy、fake timer、環境変数の差替えは `afterEach` で復元する。必要に応じてタイマーを破棄し、モジュール内の状態は `vi.resetModules` と再importで分離する。
- 外部サービスの通信・署名処理は境界でモックし、引数と返却値の利用を検証する。実際のアップロードや外部サービス内部の処理まで成功したとは記載しない。
- 認証に必要な鍵はテスト用に生成し、環境変数は `vi.stubEnv` で設定する。実環境の認証情報を読み込まないよう、必要に応じてdotenvをモックする。

## アサーションの共通ルール

- 正常系は戻り値に加え、依存先への引数、呼出し回数、必要な順序を確認する。主要な引渡しオブジェクトと公開レスポンスは、余分な項目も検出できる完全一致を基本とする。
- `toMatchObject` はケースの関心が一部項目に限られる場合に使う。同じオブジェクトを渡す契約は、値の一致だけでなく `toBe` による参照同一性も検証する。
- 書き換える項目だけでなく、更新引数やレスポンスへ含めてはいけない項目も確認する。
- `AppError` は型、`code`、`statusCode` を確認する。予期しない例外は元のErrorオブジェクトがそのまま伝播することを検証する。
- 異常系は依存処理を一つずつ失敗させ、後続の検証・署名・更新などが呼ばれないことを確認する。早期returnでは不要な検索・作成がないことも確認する。
- 複数の不備があるケースでエラーの優先順位を確認する。既に開始した並行処理の取消しなど、実装にない保証は期待しない。
- 配列・辞書は件数、順序、元index・識別子と値の対応、欠落・重複を検証する。配列を詰めた後の位置と元indexを混同しない。
- 数値境界は下限・上限の直前／一致／直後を確認し、0、負数、小数、文字列、null、undefined、欠落を区別する。空文字・空配列、optional・nullable、入れ子の各階層も対象に応じて確認する。

## 非同期処理・重複実行・並行処理

- Promiseを返す対象と非同期アサーションは必ずawaitする。開始した処理を未回収のままテストを終了しない。
- 待機や完了順の検証には `fixtures.ts` のdeferred Promiseの形式を用い、開始通知と解放用Promiseを分ける。任意のsleepや偶然の実行順に依存しない。
- 前段を保留している間に後続が実行されないこと、全処理の完了前にusecaseが成功を返さないこと、解放後に期待する順序で進むことを確認する。
- 呼出し順のassertだけでawaitを保証したとしない。待機が契約となる箇所は、Promiseを保留するテストを設ける。
- 並行処理は正順・逆順・混在、飛び飛びのindexなど、問題を再現できる手順を明示する。別呼出しの結果が混ざらないことも確認する。
- rejectを操作する場合は先に拒否の検証を登録し、残った処理も解放・回収する。途中のassertが失敗しても後片付けが必要な場合は `try/finally` を用いる。
- 逐次2回の実行と並行実行を分ける。2回目の検索結果を変えるモックでは、その前提を明記し、一般的な重複排除や一意性の保証へ拡大しない。

## 各層で確認すること

### validator・middleware

- 実schemaの `safeParse`／`parse` を使う。受理・拒否に加え、変換後の値、未知キーの除去、入力順の保持など対象の契約を確認する。
- validateBody／validateParamsの成功時は検証済み値の格納と `next` の呼出しを確認する。失敗時はエラーと、正常系の `next` や検証済み値の設定が行われないことを確認する。
- 独自refinementは拒否の有無だけでなく、エラーが付く項目・配列位置を確認する。
- schemaで受理されることと、usecaseの業務条件を満たすことを分ける。usecaseやhelperへの直接呼出しでmiddlewareの検証まで実行されると仮定しない。

### helper・service

- helperは優先順位、fallback、変換、戻り値、不要な後続呼出しの抑止を検証する。重要な結果は実usecaseへ接続し、次の処理へ正しく渡ることも確認する。
- URL等を組み立てるhelperは、既存値の再利用、新規生成条件、依存先へ渡すキーと返却URLの対応を確認する。
- serviceは依存メソッドをモックし、引数、回数、必要な順序、戻り値・参照の引渡しを確認する。モック先の実際の動作まで検証したとしない。

### controller

- usecaseをモックし、実controllerを呼ぶ。認証済みユーザー、検証済み入力、IDの扱いを確認し、未検証bodyに混入した別ユーザーID等を採用しないことを検証する。
- 成功時はステータスと返却項目を確認する。null、空配列、空辞書、値ありなどレスポンスの該当形を扱う。
- 失敗時は同じエラーを `next` へ渡し、成功レスポンスを送らないことを確認する。

### Router

- 最小のExpressアプリへJSON parserと対象Routerを明示的に接続し、Supertestで呼び出す。usecaseをモックし、認証・validator・レート制限は実処理を使う。
- 正常応答、未認証・不正・期限切れトークン、params／body不正、複数不正時の優先順位、usecaseの未実行を確認する。
- レート制限は許容回数と次の1回、ユーザー別の枠、時間窓経過後の再開、不正入力が回数に含まれるかを実装に合わせて確認する。
- 時間制御はDateやintervalなど必要な対象に限定し、HTTP I/Oを妨げない。テストごとに制限状態を分離する。
- テスト専用の4引数エラーmiddlewareを使う場合は、エラー観測用であることを明示する。この結果を実アプリのRouter登録や共通errorHandlerの検証済みという意味にしない。

## 報告書のルール

`testReport.md` は結果を先に示し、次の内容を記録する。

- 実行日、対象範囲、変更したファイル、完了した範囲。
- ファイル別と全体の実行件数、成功・失敗・skip・todoの件数。
- 実行ディレクトリ、再現できるコマンド、各確認の成否。
- 実処理とモックの範囲、テストで確認できること・確認していないこと。
- 設計ケースIDごとの判定、対応テストファイル、確認内容、残る範囲。
- 観測した挙動の入力・再現手順・実際の結果。特に並行処理は開始・完了の順序を記録する。
- 未実装・未実行・対象外・環境制約とその理由、および既知のエラーと今回の変更に起因するエラーの区別。

設計項目数と `it.each` 展開後の実行件数は別々に集計する。複数IDを一つのテストで確認する場合も対応が追えるようにする。件数は実際のランナー出力・JSONレポートから集計し、推測や過去の実行結果を今回の結果として記載しない。

「成功」「失敗」「一部実施」「対象外」「未実行」を区別する。観測テストの成功は、望ましい仕様であることや不具合の解消を意味しない。未作成・未実行のケースをskip件数や成功件数へ混ぜない。

カバレッジを取得した場合は対象と行・分岐の結果、未実行部分の理由を報告する。高い割合やテスト件数だけを完了の根拠にせず、無関係な機能や不自然なfixtureを増やして100%を目指さない。

## 修正案・追加テスト・再報告

- 修正案と追加テスト設計は `afterFix.md` にまとめ、`testReport.md` の観測事項・元のケースIDを根拠として結び付ける。未確認の事項から修正の必要性を断定しない。
- 修正ID（`F1` 等）、対象ファイル、原因、修正方針、修正後の契約、対象外を明示する。設計だけの段階では実装・検証済みと書かない。
- 追加ケースには `AF-<観点><連番>` のIDを付け、元のケースID、レベル、入力・手順、修正後の期待結果を対応表にする。
- 修正前の再現条件と修正後の期待結果を対にし、正常系、異常系、境界、後続未実行、実helperとの接続、必要な重複・並行実行を確認する。
- 既存ケースを「維持」「期待値の変更」「別の責務のテストへ移行」などに整理する。仕様が変わる箇所だけ更新し、無関係なassertを弱めない。
- 不具合の旧挙動を期待する観測テストは、修正が実装された段階で新しい契約へ移行する。旧結果は過去の報告として残す。
- 失敗を隠すための削除、skip、todo化をしない。元の件数を維持すること自体を目的にしない。
- 追加・移行後は対象ディレクトリの回帰テストを実行し、`afterFix.md` に修正レポートを追記する。変更内容、ケース対応、結果、未達事項、完了範囲を示す。
- 再修正では理由と契約の変更根拠を明記し、現行設計を更新したうえで再実行結果を追記する。以前の報告は実行履歴として残し、どの判定が最新か明確にする。

## 実行確認と完了判定

テストコードを作成・変更した場合は、`server/` で次を実行する。`<対象ディレクトリ>` は今回のusecaseのパスへ置き換える。

```bash
npm run test:run -- test/usecases/<対象ディレクトリ>/
npm run lint
npm run typecheck
./node_modules/.bin/tsc --noEmit -p test/tsconfig.json
```

- lint・型検査の実際の対象を確認する。テストTSがlint対象から外れている場合は、既存のESLintとtypescript-eslintを使って対象テストへの追加検査を行い、その方法と結果を記録する。検査を通すためだけに既存設定を変更しない。
- 既存エラーや実行環境の制限で失敗した場合は、コマンド、原因、今回の変更との関係を報告する。「変更ファイルのエラーが報告されなかった」と「検査全体が成功した」を区別する。
- 設計書・報告書だけを変更した場合は、記載・リンク・ケース対応・変更範囲を確認する。テストを再実行していない場合はその旨を明記する。
- 完了は、依頼範囲の必須ケース、異常時の後続未実行、重要な引数・戻り値、非同期処理の待機・順序、関連する回帰確認と報告の整合が確認できた範囲に限定する。
- 最後に差分を確認し、対象外のコード・テスト・設定の変更や、デバッグコードが混入していないことを確認する。
